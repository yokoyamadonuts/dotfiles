# インディー開発者 成功ロードマップ

5人の海外トップ個人開発者（Pieter Levels, Thibault Louis-Lucas, Marc Lou, Tony Dinh, Jack Friks）から抽出した成功パターンの体系化。

## Core Principles

### 1. Revenue is the Only Judge（収益だけが審判）

> "Vanity metrics don't pay the bills." — Pieter Levels

- ユーザー数、いいね数、フォロワー数は**バニティメトリクス**
- 唯一の成功指標は**MRR（月次経常収益）**
- 収益が出ないプロダクトは3ヶ月でKill or Pivotを判断する

### 2. Speed Over Perfection（完璧より速度）

> "Ship fast, fix later." — Marc Lou

- MVPは**1週間以内**に出す（理想は週末）
- Vibe Coding：プロトタイプ段階はAIに任せて**動けばOK**
- テスト・リファクタリングは**収益が出てから**
- コードの美しさより**ユーザーの反応**が重要

### 3. Distribution Before Product（プロダクトより配信）

> "Build the audience before the product." — Jack Friks

- プロダクトを作る**前に**配信チャネルを持つ
- Build in Publicで**開発過程そのものをコンテンツ**にする
- 無料ツールで集客し、有料プロダクトに転換する
- **1日1時間**はマーケティングに使う

### 4. Low Maintenance by Design（設計段階で低保守）

> "Every product you build should run itself." — Tony Dinh

- BYOKモデル（Bring Your Own Key）でインフラコストゼロ化
- 顧客サポートを最小化する設計（セルフサービス、FAQ、オートメーション）
- モノリスアーキテクチャ、サーバーレス優先
- **同じスタックを永遠に使う**（Marc Lou: 21プロダクト同一スタック）

### 5. Portfolio Approach（ポートフォリオ戦略）

> "Don't put all your eggs in one basket." — Thibault Louis-Lucas (Tibo)

- 1つのプロダクトに賭けず**3-5個を並行運用**
- 勝者に集中、敗者はKill
- 各プロダクトは独立して収益化できる状態にする
- プラットフォーム依存を避け、**収益源を分散**する

## Phase 0: 基盤構築（1-2週間）

**ゴール**: 開発速度を最大化するための基盤を整える

### スタック固定

自分の「One Stack」を決めて、すべてのプロダクトで使い回す：

| レイヤー | 推奨例 | 理由 |
|---------|--------|------|
| フロントエンド | Next.js / Nuxt | SSR + SPA両対応 |
| バックエンド | 同上（フルスタック） | コンテキストスイッチ削減 |
| データベース | Supabase / PlanetScale | マネージド + 無料枠 |
| 認証 | Clerk / Supabase Auth | 自作しない |
| 決済 | Stripe | デファクト |
| ホスティング | Vercel / Railway | ゼロコンフィグ |
| デザイン | Tailwind + shadcn/ui | コピペで高品質 |

### ボイラープレート作成

固定スタックでボイラープレートを作り、すべてのプロダクトの出発点にする：

```
my-boilerplate/
├── 認証（ログイン/サインアップ/ログアウト）
├── 決済（Stripe Checkout統合）
├── ランディングページ（価格表付き）
├── ダッシュボード（基本レイアウト）
├── メール送信（Resend統合）
└── アナリティクス（PostHog等）
```

### Build in Publicチャネル開設

- **X (Twitter)**: メインチャネル。開発ログ、収益報告、学びの共有
- **個人サイト/ブログ**: 長文コンテンツ、SEO対策
- **Product Hunt**: ローンチ時の集中的な露出

## Phase 1: 初プロダクト（1-2週間）

**ゴール**: 最速で市場に出して収益を得る

### Step 1: アイデア検証（1日）

以下のゲートを通過したアイデアだけを作る：

1. **6秒テスト**: 6秒で説明できるか？
2. **Scratch Your Own Itch**: 自分が欲しいか？
3. **支払いテスト**: 48時間のランディングページで「買う」ボタンを押す人がいるか？
4. **競合確認**: 競合がいることは**良い兆候**（市場がある証拠）
5. **Build可能性**: 自分のスタックで1週間以内に作れるか？

→ 詳細は `validate-idea` スキルを使用

### Step 2: MVP構築（3時間〜5日）

| 速度 | 期間 | 手法 | 適用場面 |
|------|------|------|---------|
| Vibe Coding | 3時間〜1日 | AIに任せて最速で出す | アイデア検証、プロトタイプ |
| Weekend MVP | 2-5日 | 週末で完成させる | 小規模SaaS、ツール |
| Standard MVP | 1-2週間 | 通常のMVP開発 | やや複雑なプロダクト |

**必須**: Day 1でStripe Checkoutを統合する。**価格ページを最初に作る。**

→ 詳細は `mvp-scaffolding` スキルを使用

### Step 3: ローンチ

マルチプラットフォーム同時ローンチ：
- Product Hunt
- X (Twitter)
- Hacker News
- Reddit（関連サブレディット）
- IndieHackers

→ 詳細は `launch-playbook` スキルを使用

### Step 4: 収益検証（30日以内）

| 指標 | 判断 |
|------|------|
| 有料ユーザー0人 | Pivot or Kill |
| 有料ユーザー1-5人 | 改善して継続 |
| MRR $100+ | 勝者候補。投資を増やす |

## Phase 2: マーケティングシステム（Phase 1と並行）

**ゴール**: 持続的な流入を作る

### 1日1時間マーケティングシステム（Jack Friks方式）

| 時間 | 活動 |
|------|------|
| 15分 | X投稿（進捗、学び、数字） |
| 15分 | コミュニティ参加（Reddit、Discord、IndieHackers） |
| 15分 | コンテンツ作成（ブログ、スレッド） |
| 15分 | 分析・最適化（何が効いているか確認） |

### コンテンツ戦略

#### 無料ツールファネル（Marc Lou方式）

1. **無料ツールを作る**: 有料プロダクトの一部機能を無料で提供
2. **SEOで流入**: 「free [tool name]」で検索上位を狙う
3. **有料版にアップセル**: 「もっと機能が欲しい？有料版はこちら」

#### Build in Publicコンテンツ

- **進捗共有**: 「今日作ったもの」「今週の成果」
- **収益透明性**: 「MRR $X達成」「X人の有料ユーザー」
- **技術的な学び**: 「このスタックで失敗した理由」「この設計が効いた」
- **ストーリー**: 「なぜこのプロダクトを作ったか」

→ 詳細は `build-in-public` スキルを使用

## Phase 3: ポートフォリオ展開（3-6ヶ月）

**ゴール**: 収益源を分散し、勝者を見つける

### 3-5プロダクト展開

Phase 1のサイクルを繰り返し、3-5個のプロダクトを並行運用する：

```
プロダクトA: MRR $500  ← 勝者候補
プロダクトB: MRR $50   ← 改善中
プロダクトC: MRR $0    ← Kill検討
プロダクトD: ローンチ直後
```

### PMFサイクル（Tibo方式）

各プロダクトを4ステージで管理する：

| ステージ | 状態 | アクション |
|---------|------|-----------|
| 検証中 | ローンチ前〜初期 | ユーザーフィードバック収集 |
| 成長中 | 有料ユーザーあり | マーケティング強化 |
| 安定 | MRR安定 | 低保守モードに移行 |
| Kill | 3ヶ月収益なし | 撤退、学びを記録 |

### BYOKモデル検討（Tony Dinh方式）

AI機能を持つプロダクトの場合：

- ユーザーが自分のAPIキーを持ち込む（BYOK: Bring Your Own Key）
- **メリット**: インフラコストゼロ、スケーリングの心配なし
- **デメリット**: UXがやや複雑、APIキー管理の説明が必要
- **判断基準**: AI APIコストがMRRの20%を超えるならBYOK検討

---

## Phase 4: スケール（6ヶ月〜）

**ゴール**: 勝者プロダクトに集中し、持続可能なビジネスにする

### 勝者の特定

ポートフォリオから勝者を特定する基準：

| 指標 | 勝者の基準 |
|------|-----------|
| MRR | $1,000+で安定成長 |
| チャーン率 | 月5%以下 |
| 自然流入 | 広告なしでユーザーが増えている |
| 口コミ | ユーザーが他人に推薦している |

### アウトプットゴール > アウトカムゴール（Marc Lou方式）

- **アウトカムゴール**（避ける）: 「MRR $10Kにする」→ コントロールできない
- **アウトプットゴール**（推奨）: 「毎週1機能リリース」→ コントロールできる

自分がコントロールできるアクションにフォーカスする。

### 長期モート構築

| モートの種類 | 例 |
|-------------|---|
| ネットワーク効果 | ユーザーが増えるほど価値が上がる |
| データモート | ユーザーデータの蓄積 |
| ブランド | Build in Publicで構築した信頼 |
| スイッチングコスト | データ移行の手間 |
| SEOモート | 長期的なオーガニック流入 |

## Anti-Patterns（やってはいけないこと）

### 1. 作り込みすぎ（Over-Engineering）

- MVP段階でマイクロサービスにする
- テストカバレッジ100%を目指す
- 「完璧になったらローンチする」
- **対策**: 「恥ずかしいぐらいでちょうどいい」

### 2. マーケティング無視

- 「良いプロダクトは勝手に売れる」
- ローンチしただけで終わり
- SNSをやらない
- **対策**: 1日1時間マーケティングシステム

### 3. プラットフォーム依存

- App Store/Google Playのみで配信
- 単一のAPIプロバイダに依存
- 特定のSNSプラットフォームのみに依存
- **対策**: ウェブファースト、複数チャネル

### 4. バニティメトリクスに騙される

- 「ユーザーが気に入っている」（でも払わない）
- 「1000人がサインアップした」（でも10人しか使っていない）
- 「SNSでバズった」（でも収益ゼロ）
- **対策**: MRR、有料ユーザー数だけを見る

### 5. 1つのプロダクトに固執

- 3ヶ月収益ゼロでも続ける
- 「次の機能を追加すれば売れるはず」
- サンクコスト効果に支配される
- **対策**: Kill or Keep判定を定期的に実施

### 6. 自分のかゆいところを掻かない

- 自分が使わないプロダクトを作る
- 市場調査だけでアイデアを決める
- **対策**: Scratch Your Own Itchテスト
