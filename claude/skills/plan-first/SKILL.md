# Plan First Workflow

Claude Codeで最も重要な3つの原則。

## 核心原則

1. **Plan Modeを使う** - いきなりコードを書かない
2. **Planをdocs/に保存** - 計画をプロジェクトにコミット
3. **過去のPlanを最初に探索** - コードベース理解の起点にする

## ワークフロー

### 1. 新しいタスク開始時

```
ユーザー: 「〇〇を実装して」
```

**即座にコードを書かない。まずPlan Modeに入る。**

1. `shift+tab` でPlan Modeに切り替え
2. 要件を整理し、実装計画を作成
3. 計画が承認されたら `docs/plans/` に保存
4. 実装開始

### 2. Plan保存形式

プロジェクトの `docs/plans/` ディレクトリに保存：

```
{project}/
├── docs/
│   └── plans/
│       ├── 2025-01-15-user-auth.md
│       ├── 2025-01-20-api-refactor.md
│       └── 2025-02-01-performance-fix.md
└── src/
```

**ファイル命名規則**: `YYYY-MM-DD-{slug}.md`

**Planテンプレート**:

```markdown
# {タイトル}

## 背景
- なぜこの変更が必要か
- 現状の問題点

## 目標
- 達成したいこと（箇条書き）

## 設計方針
- アーキテクチャ上の決定事項
- 選択したアプローチと理由
- 却下した代替案

## 実装計画
1. ステップ1: ...
2. ステップ2: ...
3. ステップ3: ...

## 影響範囲
- 変更されるファイル/モジュール
- 既存機能への影響

## テスト計画
- 確認すべき項目

## 完了条件
- [ ] 条件1
- [ ] 条件2
```

### 3. コードベース探索時

**新しいプロジェクトや機能を理解する際、最初に過去のplanを探索する。**

```bash
# 過去のplanを確認
ls docs/plans/
rg "検索キーワード" docs/plans/
```

過去のplanから得られる情報：
- **設計意図**: なぜこの構造になっているか
- **却下案**: 試して失敗したアプローチ
- **コンテキスト**: 当時の制約や要件

### 4. Plan保存コマンド

Plan作成後、以下を実行：

```bash
# docs/plans ディレクトリを作成（初回のみ）
mkdir -p docs/plans

# Planファイルを作成
# ファイル名: YYYY-MM-DD-{slug}.md
```

## プロアクティブな発動

以下の状況で自動的にこのワークフローを適用：

### Planを先に書くべき場面
- 「〇〇を実装して」「〇〇を追加して」
- 「〇〇をリファクタリングして」
- 「〇〇のバグを直して」（複雑な場合）
- 要件が曖昧なとき

### 過去のPlanを探索すべき場面
- 「このコードの設計意図は？」
- 「なぜこの実装になっている？」
- 「〇〇について教えて」（プロジェクト固有の質問）
- 新しい機能を既存コードに追加するとき

## アンチパターン

❌ **即コード**: 要件を聞いてすぐ実装を始める
❌ **Plan使い捨て**: 承認後にPlanを保存しない
❌ **コードだけ探索**: docs/plans/を無視してコードだけ読む
❌ **巨大Plan**: 1つのPlanに複数の無関係な変更を詰め込む

## なぜこれが重要か

- **Plan Mode**: 8割の時間を計画に使うことで手戻りを防ぐ
- **永続化**: 計画はプロジェクトの「意思決定ログ」になる
- **探索起点**: 過去のplanはコードより「なぜ」を説明している

> skills, MCP, エージェントより、この3原則の方が遥かに生産性に影響する。
