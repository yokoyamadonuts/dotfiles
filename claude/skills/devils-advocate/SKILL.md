# Devil's Advocate スキル

## 概要

計画・戦略・設計・PRDを構造的に批判し、弱点を事前に発見して強化する。確認バイアスを排除し、高品質な意思決定を支援する。

## なぜ重要か

戦略や計画を立てると、自然に：
- 支持するエビデンスを探してしまう
- 反対のエビデンスを軽視してしまう
- 懸念事項を合理化してしまう
- アイデアに感情的に執着してしまう

構造化された批判で、これらのバイアスを排除する。

## コアワークフロー

### ステップ1: 対象の把握

ストレステスト対象のドキュメントを読み込む：
- 戦略書、PRD、設計書、計画書など
- 関連するコンテキスト情報

### ステップ2: 仮定の洗い出し

対象ドキュメントから暗黙の仮定を抽出する：

各仮定について「これが成立するために何が真でなければならないか？」を検証する。

例：
| 仮定 | 検証方法 | リスク |
|------|---------|--------|
| ユーザーは音声UIを好む | 50人のユーザーテスト | 高 |
| AIコストは$2/ユーザー/月以下 | プロトタイプで実測 | 中 |
| 競合は6ヶ月以内にコピーしない | 技術的障壁の分析 | 高 |

### ステップ3: 構造化された批判

5つのカテゴリで攻撃的に批判する：

#### DIAGNOSIS（診断）への挑戦
- 「正しい問題を解決しているか？エビデンスは？」
- 「タイミングは正しいか？市場が準備できていない可能性は？」
- 「顧客を本当に理解しているか？バイアスはないか？」

#### GUIDING POLICY（基本方針）への挑戦
- 「なぜ顧客は我々を選ぶか？代替品と比べてどうか？」
- 「なぜ競合はこれをコピーできないか？6ヶ月後はどうか？」
- 「何を諦めているか？それは本当に価値が低いのか？」
- 「この領域で勝つ権利があるか？不公平な優位性は何か？」

#### COHERENT ACTIONS（アクション）への挑戦
- 「本当に実行可能か？リソースは足りるか？」
- 「これらの施策は本当に互いを強化しているか？」
- 「単一障害点はどこか？何が起きたらすべてが崩壊するか？」
- 「機会コストは？やらないことの価値は？」

#### インディー開発者特有の挑戦（ソロ/小規模チームの場合）
- 「1人で保守できるか？3年後も？」
- 「プラットフォーム依存リスクは？App Store / 特定API / 特定SNS」
- 「収益のない期間をどれだけ耐えられるか？」
- 「このプロダクトがうまくいかなかった場合、学びを次に活かせるか？」
- 「マーケティングの計画はあるか？Build in Publicだけで十分か？」

#### 技術的な挑戦（該当する場合）
- 「技術が期待通りに動かなかったら？」
- 「技術がコモディティ化したら？差別化は消えないか？」

#### 成長の挑戦（該当する場合）
- 「成長の仮定が間違っていたら？CACが3倍だったら？」
- 「ターゲット顧客にリーチできなかったら？」

### ステップ4: Pre-mortem（事前検死）

「12ヶ月後にこの戦略/計画が完全に失敗した。なぜか？」

失敗の事後分析を書く：
- 何が間違ったか
- どの仮定が崩れたか
- どの外部要因が影響したか
- 何を見落としていたか

### ステップ5: 「成立条件」フレームワーク

各重要な仮定に対して：

```markdown
## 仮定: [仮定の内容]

### 成立条件
1. [条件1] - 検証方法: [どうテストするか]
2. [条件2] - 検証方法: [どうテストするか]
3. [条件3] - 検証方法: [どうテストするか]

### リスク評価
- 仮定が崩れる確率: [高/中/低]
- 崩れた場合の影響: [壊滅的/重大/軽微]
- 軽減策: [Plan B]
```

### ステップ6: レッドフラグの検出

以下の発言パターンを検出したら警告する：

| レッドフラグ | 問題 |
|-------------|------|
| 「競合より上手く実行する」 | 戦略ではなく願望 |
| 「明らかに良いアイデア」 | 明らかなら他社がやっている |
| 「顧客は気に入るはず」 | エビデンスに基づいているか？ |
| 「先行者優位がある」 | 先行者優位は稀 |
| 「大きな市場だ」 | 獲得できるとは限らない |
| 「直接の競合はいない」 | 代替品の競合は必ずいる |
| 「App Storeで配信する」 | プラットフォームリスク: 規約変更で収益が消える可能性 |
| 「APIに依存している」 | 値上げ/停止リスク: 外部API依存はコスト構造が不安定 |
| 「無料ユーザーが多い」 | 無料ユーザーは顧客ではない。有料転換率を確認せよ |
| 「ユーザーが気に入っている」 | バニティメトリクス。「気に入る」と「金を払う」は別問題 |

### ステップ7: 強化提案

批判を建設的な改善に変換する：

```markdown
## 弱点と強化策

### 弱点1: [弱点の説明]
- **弱い回答**: [現状の対応]
- **強い回答**: [改善案]
- **検証方法**: [どう確認するか]

### 弱点2: ...
```

### ステップ8: 戦略を殺すべき条件

以下の場合は戦略の撤回を勧告する：
1. 重要な仮定が検証できない（リスクが高すぎる）
2. 明確な差別化がない（競合がすぐコピーできる）
3. 機会コストが高すぎる（他の選択肢が明らかに優れている）
4. チームに実行能力がない
5. 経済性が成り立たない（収益化できない）

## 出力形式

```markdown
# Devil's Advocate レポート

対象: [ドキュメント名]
日付: [日付]

## エグゼクティブサマリー
[3つの最も重要な発見]

## 仮定の検証
[仮定のリストと検証結果]

## 構造化された批判
### DIAGNOSIS への挑戦
### GUIDING POLICY への挑戦
### COHERENT ACTIONS への挑戦

## Pre-mortem
[失敗シナリオ]

## 成立条件
[各仮定の成立条件と検証方法]

## レッドフラグ
[検出されたレッドフラグ]

## 強化提案
[弱点と改善案]

## 総合評価
- 戦略の堅牢性: [高/中/低]
- 最大のリスク: [概要]
- 推奨アクション: [次のステップ]
```
