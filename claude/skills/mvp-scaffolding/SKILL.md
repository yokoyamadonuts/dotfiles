# MVPプロジェクト初期構築スキル

## 概要

MVPを最速で出荷するためのプロジェクト初期構築を支援する。核心は「何を作らないかを決める」こと。認証、決済、エラートラッキング等の共通機能は既製品を使い、プロダクトのコア価値に開発リソースを集中させる。

## ユースケース

- 新規SaaSプロダクトのMVP立ち上げ
- ハッカソン・プロトタイプの高速構築
- サイドプロジェクトの技術スタック決定
- 既存アイデアの技術的な実現可能性検証

### ステップ2: 必要機能の洗い出しとBuy vs Build判定

以下のカテゴリごとに「必要か」「Build vs Buy」を判定する：

| カテゴリ | 必要？ | デフォルト推奨 | 理由 |
|---------|--------|---------------|------|
| 認証・認可 | | Buy | セキュリティリスクが高すぎる |
| 決済・課金 | | Buy | PCI DSS準拠が大変 |
| メール送信 | | Buy | 到達率の最適化が難しい |
| ファイルアップロード | | Buy | エッジケースが多い |
| 検索 | | 規模による | 小規模なら自作可 |
| リアルタイム通信 | | 規模による | WebSocketは自前でも可 |
| エラートラッキング | | Buy | Sentry等が圧倒的に成熟 |
| アナリティクス | | Buy | PostHog等のコスパが良い |
| CMS | | 要件による | ヘッドレスCMS vs 自前 |
| デプロイ・ホスティング | | Buy | Vercel/Railway等が楽 |

```javascript
AskUserQuestion({
  questions: [
    {
      question: "以下の機能のうち、必要なものはどれですか？",
      header: "必要機能",
      options: [
        { label: "認証・認可", description: "ログイン、SSO、権限管理" },
        { label: "決済・課金", description: "支払い、サブスクリプション" },
```

必要な機能ごとに `build-or-buy` スキルの判定ロジックを簡易適用する。複雑な判断が必要な場合は `build-or-buy` スキルへ委譲する。

### ステップ2.5: Day 1 マネタイゼーション（必須）

**収益化は初日に組み込む。後回しにしない。**

- [ ] **Stripe Checkoutを初日で統合する**（ボイラープレートに含める）
- [ ] **価格ページを最初に作る**（プロダクトの前に価格を決める）
- [ ] **48時間の「買うボタンテスト」でバリデーション**

```
判定基準:
- 購入者あり → 即座に本格開発
- 問い合わせのみ → メッセージング修正して再テスト
- 反応なし → アイデアを変える or ターゲットを変える
```

→ 詳細は `validate-idea` スキルの「Gate 3: 支払いテスト」を参照

### ステップ3: スタック選定

プロダクト種別とチーム規模に応じたスタックを提案する。

**提案の原則**:
- チームが既に知っている技術を優先
- 採用実績が豊富なエコシステムを選ぶ
- MVP段階では新技術への挑戦を避ける
- **同じスタックを永遠に使う**（Marc Lou: 21プロダクト同一スタック。コンテキストスイッチこそ最大の時間泥棒）
- **ボイラープレートを資産にする**（認証+決済+LP+ダッシュボードの雛形を全プロダクトで再利用）
- **BYOKモデルを検討する**（Tony Dinh方式: AI機能のインフラコストをゼロ化。ユーザーが自分のAPIキーを持ち込む）
- 必要なら `competitive-research` スキルで詳細比較

### ステップ4: フォルダ構造ドキュメント生成

選定したスタックに基づく推奨フォルダ構造を生成する。

**原則**:
- 機能ベースのコロケーション（技術ベースではなく）
- 初期はフラットに、必要に応じてネスト
- テストはソースの隣に配置

### ステップ5: セットアップチェックリストと.env.example生成

実行可能なセットアップ手順をチェックリスト形式で出力する。

## やらないことリスト（DON'Ts）

MVP段階で避けるべきことを明示する：

- **マイクロサービスにしない** - モノリスから始める
- **認証を自作しない** - 既製品を使う
- **CSSフレームワークを自作しない** - Tailwind + shadcn/ui 等
- **完璧なCI/CDを組まない** - 最小限のパイプラインから
- **過度なテストを書かない** - クリティカルパスのみ
- **国際化を最初からやらない** - 1言語でローンチ
- **マルチテナントを最初から設計しない** - シングルテナントで検証
- **独自のデザインシステムを作らない** - 既存コンポーネントライブラリを使う

## MVP速度ベンチマーク

| アプローチ | 目標期間 | 危険ライン |
|-----------|---------|-----------|
| Vibe Coding | 3時間〜1日 | 2日超 |
| Weekend MVP | 2-5日 | 1週間超 |
| Standard MVP | 1-2週間 | 2週間超 |

**2週間を超えたら危険信号**。スコープを削るか、アイデアを見直す。

> "If you can't build it in a weekend, you're building too much." — Marc Lou
