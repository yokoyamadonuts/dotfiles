# 設計意図レビュースキル

## 概要

コードレビューの真の目的は「メンタルモデル（設計思想）の共有」である。バグ発見や品質チェックは副産物に過ぎない。このスキルは、変更の「WHY」を明示化し、チーム全体の設計理解を揃えることに集中する。

**Google公式ガイドライン**: 「コードベース全体の健全性が時間とともに改善されていること」の確認。

**既存 `/review` との補完関係**:
- `/review` → 技術品質チェック（WHAT: コード品質、セキュリティ、テスト等）
- `/design-intent` → 設計意図の共有（WHY: なぜこの設計か、何を犠牲にしたか）

## コアワークフロー

### ステップ1: 変更検出・コンテキスト収集

git差分と関連コンテキストを収集する。

**差分取得**:
```bash
git diff --staged
git diff
git log --oneline -5
```

**コンテキスト収集**:
- 変更ファイルをReadで読み込む
- 変更ファイルのインポート先・呼び出し元をGrepで追跡
- `docs/DESIGN.md`, `CLAUDE.md` があれば読み込む
- PRの説明文やコミットメッセージがあれば確認

**変更の規模判定**:
- 小（1-3ファイル、50行以下）→ 軽量レビュー（ステップ2-3中心）
- 中（4-10ファイル、50-200行）→ 標準レビュー（全ステップ）
- 大（10ファイル超、200行超）→ 重点レビュー（ステップ4を厚く）

### ステップ2: 設計意図の確認（対話フェーズ）

ソクラテス式質問で作者に「WHY」を問う。AskUserQuestionで対話する。

#### 2-1: 変更の動機

```javascript
AskUserQuestion({
  questions: [
    {
      question: "この変更の主な動機は何ですか？",
      header: "変更の動機",
      options: [
        { label: "新機能", description: "新しいユースケースへの対応" },
        { label: "リファクタリング", description: "既存コードの構造改善（機能変更なし）" },
        { label: "バグ修正", description: "既知の不具合の修正" },
        { label: "パフォーマンス改善", description: "速度・メモリ等の最適化" }
      ],
      multiSelect: false
    }
  ]
})
```

#### 2-2: 設計判断の深掘り

変更内容を分析した上で、以下の質問を投げかける（最も重要な1-2個を選択）:

| 質問カテゴリ | 質問例 |
|-------------|--------|
| 代替案 | 「他にどんなアプローチを検討しましたか？なぜこれを選びましたか？」 |
| 制約 | 「この設計を制約している要因は何ですか？（技術的制約、時間、互換性等）」 |
| 将来性 | 「この設計は将来の変更にどう対応しますか？意図的に拡張ポイントを作りましたか？」 |
| 境界 | 「この変更のスコープをどこで線引きしましたか？意図的に含めなかったものは？」 |

**重要**: 質問は変更内容に基づいて具体的にカスタマイズする。汎用的な質問ではなく「この差分のこの部分はなぜこうしたのか」と聞く。

### ステップ3: トレードオフ分析

変更に含まれるトレードオフを明示化する。

#### 3-1: トレードオフの特定

コード差分から以下のトレードオフを検出・分析する:

| トレードオフ軸 | 問い |
|---------------|------|
| シンプルさ vs 柔軟性 | 直接的な実装か、抽象化を挟んでいるか |
| パフォーマンス vs 可読性 | 最適化のために可読性を犠牲にしていないか |
| DRY vs 明確性 | 共通化で文脈が失われていないか |
| 完全性 vs スピード | 意図的にスコープを絞っているか |
| 安全性 vs 利便性 | バリデーションやエラーハンドリングの粒度 |

#### 3-2: トレードオフの確認

特定したトレードオフを作者に確認する:

```javascript
AskUserQuestion({
  questions: [
    {
      question: "[検出したトレードオフ]について、この判断は意図的ですか？",
      header: "トレードオフ",
      options: [
        { label: "意図的", description: "理由があってこの判断をした" },
        { label: "気づいていなかった", description: "別のアプローチを検討したい" },
        { label: "妥協", description: "制約（時間・技術等）によるもの" }
      ],
      multiSelect: false
    }
  ]
})
```

- 「意図的」→ 理由をレポートに記録。妥当であれば次へ進む。
- 「気づいていなかった」→ 代替案を提示して再検討を促す。
- 「妥協」→ TODOコメントやIssue作成を提案。技術的負債として記録。

### ステップ4: 影響範囲マッピング

技術的影響だけでなく、メンタルモデルへの影響も分析する。

#### 4-1: 技術的影響

Grep/Globで依存関係を追跡:
- この変更を使う側（呼び出し元）への影響
- この変更が使う側（依存先）への影響
- APIの互換性（公開インターフェースの変更有無）

#### 4-2: メンタルモデルへの影響

以下の観点で「チームの理解に影響するか」を評価:

| 影響レベル | 説明 | 例 |
|-----------|------|-----|
| 局所的 | 変更ファイル内で完結 | 関数内ロジックの改善 |
| モジュール的 | 同一モジュール内に影響 | 内部APIの変更 |
| 構造的 | アーキテクチャの前提を変更 | 新しい設計パターンの導入 |
| 概念的 | ドメインモデルの理解を変更 | 用語の変更、責務の再定義 |

**構造的・概念的影響がある場合**: ドキュメント更新（DESIGN.md等）の必要性を指摘する。

### ステップ5: AI生成コード検証（該当時のみ）

AI（Copilot, Claude等）で生成されたコードが含まれる場合、特別な検証を行う。

#### 5-1: AI生成コードの検出

以下のシグナルで検出を試みる:
- コミットメッセージに「Copilot」「Claude」「AI」「generated」等の言及
- 一度に大量のボイラープレートコードが追加されている
- コードスタイルがプロジェクトの既存パターンと微妙に異なる

#### 5-2: 理解度の確認

AI生成コードが疑われる場合:

```javascript
AskUserQuestion({
  questions: [
    {
      question: "この変更にはAI生成コードが含まれていますか？含まれている場合、コードの動作を自分の言葉で説明できますか？",
      header: "AI生成コード",
      options: [
        { label: "AI未使用", description: "すべて手書きのコード" },
        { label: "AI使用・理解済み", description: "AI生成だが内容を理解し、必要に応じて修正した" },
        { label: "AI使用・確認中", description: "AI生成で、まだ完全には理解していない部分がある" }
      ],
      multiSelect: false
    }
  ]
})
```

- 「AI使用・確認中」→ 理解が不十分な箇所を特定し、説明を求める。「このコードをあなたの言葉で説明してください」と促す。
- **原則**: AI生成コードを出荷する責任は作成者にある。理解していないコードは出荷すべきでない。

### ステップ6: 出荷判断レポート

全フェーズの結果を統合し、出荷判断を行う。

#### 判定基準

| 判定 | 条件 |
|------|------|
| **APPROVED** | 設計意図が明確、トレードオフが妥当、影響範囲が把握されている |
| **NEEDS DISCUSSION** | 設計判断に未解決の疑問がある、トレードオフの妥当性が不明 |
| **BLOCKED** | 設計意図が不明、影響範囲が未把握、AI生成コードの理解が不十分 |

## 出力ファイル

- `docs/design-intent-[YYYY-MM-DD].md` - 設計意図レビューレポート

### レポートテンプレート

```markdown
# Design Intent レビュー

実施日: [日付]
対象: [ブランチ名 or PR番号]
総合判定: [APPROVED / NEEDS DISCUSSION / BLOCKED]

## 変更概要
- 動機: [新機能 / リファクタリング / バグ修正 / パフォーマンス改善]
- 規模: [小 / 中 / 大]
- 変更ファイル数: [N]

## 設計意図
### WHY: なぜこの変更が必要か
[作者の説明]

### HOW: なぜこのアプローチを選んだか
[検討した代替案と選択理由]

## トレードオフ
| 判断 | 優先したもの | 犠牲にしたもの | 妥当性 |
|------|-------------|---------------|--------|
| [判断1] | [優先事項] | [犠牲事項] | [妥当/要検討/技術的負債] |

## 影響範囲
### 技術的影響
- [影響を受けるモジュール/ファイル]

### メンタルモデルへの影響
- 影響レベル: [局所的 / モジュール的 / 構造的 / 概念的]
- ドキュメント更新の必要性: [あり / なし]

## AI生成コード（該当時）
- 使用有無: [あり / なし]
- 理解度: [理解済み / 確認中]
- 要確認箇所: [具体的な箇所]

## 出荷判断
- **判定**: [APPROVED / NEEDS DISCUSSION / BLOCKED]
- **理由**: [判定の根拠]
- **次のアクション**: [必要なアクション]
```

## 関連スキル

- **`/review`**: 技術品質チェック（WHAT）を担当。`/design-intent` とセットで使用推奨
- **devils-advocate**: 戦略・計画レベルのストレステスト。設計判断の妥当性に疑問がある場合に使用
- **ship-check**: プロダクトレベルの出荷判断。`/design-intent` はコード変更単位の判断
- **analyzing-requirements**: 設計意図を新しい要件に落とし込む際に使用
