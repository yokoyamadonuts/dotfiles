# UI Design Specification Builder

AppleのシニアUIデザイナーとして、公開可能な包括的UI設計仕様書を構築する。

## 前提条件

以下が既に存在すること:

- **デザインシステム**: コンポーネント定義、デザイントークン（カラー・タイポグラフィ・スペーシング等）
- **ブランドアイデンティティ**: ボイスマトリクス、メッセージ階層、ブランドパーソナリティ
- **設計書 / PRD**: 画面一覧、情報アーキテクチャ、データモデル、API設計
- **ペルソナ / ユーザージャーニー**: ターゲットユーザーの課題と行動シナリオ

**ゼロからの場合**: まず `building-design-system` → `building-brand-identity` → 設計書作成 の順でスキルを実行してから本スキルを使用する。

## Process

### Phase 1: コンテキスト収集（並列調査）

以下を **並列** で調査する:

1. **デザインシステム**: コンポーネント一覧（ID・バリアント・サイズ）、デザイントークン（カラー・タイポグラフィ・スペーシング・エレベーション・モーション）、Do/Don't
2. **ブランドアイデンティティ**: ボイスマトリクス（4軸 × 6文脈）、メッセージ階層（タグライン → ナラティブ）、禁止語リスト
3. **設計書**: 画面一覧、IA（サイトマップ・画面遷移）、データモデル、API エンドポイント、機能要件
4. **ペルソナ / ユーザージャーニー**: ターゲットの課題・壁・行動シナリオ、コンバージョンポイント

**重要**: デザインシステムのコンポーネントIDをそのまま参照する。独自の命名を作らない。

### Phase 2: 設計哲学と全体構造（Part 1）

プロジェクトの `docs/` ディレクトリに `ui-design.md` を出力開始。

#### Part 1 の必須セクション

```
1. 設計ミッション
   - ペルソナの課題（表形式: 壁 → ペルソナの声 → UIの解決策）
   - UIが果たす役割（3つの誓約形式）
   - デザイン原則の画面適用マッピング（表形式）

2. 情報アーキテクチャ（IA）
   - サイトマップ（ASCIIツリー図）
   - 画面遷移図（ASCII矢印図）
   - ペルソナの典型的ユーザージャーニー（ステップ表）

3. ナビゲーション設計
   - モバイル: BottomTabBar構成（表形式: アイコン/ラベル/遷移先）
   - デスクトップ: Sidebar構成（表形式）
   - Immersive Mode定義（没入型画面の特別ルール）
   - 遷移ルール（表形式: from → trigger → to → animation）

4. レイアウトパターン
   - 共通グリッド適用ルール（ブレイクポイント別）
   - 画面テンプレート（ASCIIレイアウト図 × 3-4パターン）
   - スペーシング適用ルール

5. プラットフォームルール
   - プラットフォーム固有の制約
   - HIG / Material Design 準拠ポイント
   - パフォーマンスバジェット（FCP/LCP/CLS/バンドルサイズ）
```

→ ユーザーに Part 1 完成を確認してから Phase 3 へ

### Phase 3: 画面仕様（Part 2）

各画面で以下 **7セクション** を必須とする:

#### 7セクション仕様

各セクションの詳細仕様・テンプレートは [ui-design-references/screen-section-specs.md](ui-design-references/screen-section-specs.md) を参照。

```
1. ワイヤーフレーム（ASCIIアート）
   - モバイル幅（375px相当）の構造図
   - 要素の配置・サイズ・余白を視覚的に表現
   - ステップがある画面は全ステップ分のワイヤーフレーム

2. 使用コンポーネント一覧（表形式）
   - コンポーネント名 | DS参照（セクション番号） | 用途
   - デザインシステムのIDを正確に参照

3. インタラクション仕様（表形式）
   - ユーザーアクション → システム応答 → 遷移先
   - アニメーション・トランジション種別を明記

4. 空の状態（Empty State）
   - 初回アクセス / データなし時のUI
   - イラスト + コピー + CTA の定義
   - ボイスマトリクス参照（該当文脈のトーン指定）

5. エラー状態（Error State）
   - ネットワーク / サーバー / バリデーションエラー別
   - エラーメッセージのコピー（ボイスマトリクス準拠）
   - リカバリーアクション

6. ローディング状態（Loading State）
   - Skeleton / Spinner / Progressive の使い分け
   - 各コンポーネントのSkeleton仕様（サイズ・アニメーション）
   - 表示遅延しきい値（300ms / 1s / 3s）

7. デザイナーズノート
   - 設計判断の根拠（なぜこの構造にしたか）
   - トレードオフ（何を犠牲にして何を優先したか）
   - 将来の改善ポイント
```

**画面数が多い場合の分割戦略**:

- 5画面以下: 一括で作成
- 6-10画面: 前半・後半に分割（各4-5画面）
- 11画面以上: 3-4画面ずつのバッチで作成

→ 各バッチ完了後にユーザー確認を挟む

### Phase 4: 横断的仕様（Part 3）

#### Part 3 の必須セクション

```
1. ボタン・フォーム・カード適用ルール
   - 各コンポーネントの画面別適用パターン
   - バリアント選択基準

2. データ可視化仕様
   - グラフ・チャートの種類と適用場面
   - 軸ラベル・凡例・アクセシビリティ対応
   - レスポンシブ時の挙動

3. アクセシビリティ仕様（WCAG AA）
   - フォーカス管理（タブ順序 × 画面）
   - スクリーンリーダー対応（aria属性一覧）
   - キーボードナビゲーション
   - カラーコントラスト検証

4. マイクロインタラクション
   - フィードバック（成功/エラー/情報）
   - トランジション定義（進入/退出/共有要素）
   - Reduce Motion 対応

5. レスポンシブ挙動
   - ブレイクポイント別のレイアウト変更（表形式）
   - コンポーネントの適応ルール
   - 非表示 / 統合 / 変形のルール

6. DSコンポーネント使用マトリクス（付録）
   - 全画面 × 全コンポーネントの使用有無（表形式）
```

### Phase 5: 品質検証

#### ユーザー確認ポイント

- [ ] Phase 2 後: Part 1（設計哲学 & 全体構造）の承認
- [ ] Phase 3 中: 画面バッチごとの中間レビュー
- [ ] Phase 4 後: Part 3（横断的仕様）の最終レビュー

#### 検証フィードバックループ

最終完成後に以下のサイクルを実行する:

1. **実行**: 品質チェックリストの全項目を順に検証
2. **検証**: 不合格項目をリストアップし、該当箇所を特定
3. **修正**: 不合格項目を修正（画面仕様 → 横断仕様 → 全体構造の順）
4. **再検証**: 修正箇所を再チェックし、全項目パスまで繰り返す

## 品質チェックリスト

- [ ] 全画面 × 7セクション（ワイヤーフレーム・コンポーネント・インタラクション・Empty・Error・Loading・ノート）が含まれている
- [ ] ASCIIワイヤーフレームがモバイル幅で全画面に存在する
- [ ] DSコンポーネント参照が正確（セクション番号と一致）
- [ ] ボイスマトリクスの文脈指定が Empty / Error 状態のコピーに反映されている
- [ ] 1画面1CTA原則が全画面で守られている
- [ ] ナビゲーション遷移が画面遷移図と整合している
- [ ] アクセシビリティ仕様がWCAG AAを満たしている
- [ ] レスポンシブ挙動が全ブレイクポイントで定義されている
- [ ] パフォーマンスバジェットが明示されている
- [ ] DSコンポーネント使用マトリクスが全画面をカバーしている

## 重要原則

1. **1画面1CTA**: 各画面の主要アクションは1つだけ。3秒で次のアクションが分かる設計
2. **デザインシステムファースト**: 全UIをDSコンポーネントで構成する。カスタム要素は最小限
3. **3状態の完全定義**: Empty / Error / Loading は「あれば良い」ではなく必須。ユーザー体験の80%は正常系以外
4. **ブランドボイスの一貫性**: UIコピーはボイスマトリクスの文脈指定に従う。感覚ではなくシステムで管理
5. **透明な器**: UIは意識されないほど自然であるべき。コンテンツと対話が主役

## 規模スケーリング

| プロジェクト規模 | 画面数目安 | Part 2 の戦略 | Part 3 の深度 |
|----------------|-----------|--------------|--------------|
| 小規模 | 3-5画面 | 一括作成 | セクション 1-4 必須、5-6 は簡易版可 |
| 中規模 | 6-10画面 | 2バッチに分割 | 全6セクション + DSコンポーネント使用マトリクス |
| 大規模 | 11画面以上 | 3-4画面ずつバッチ | 全6セクション + マトリクス + デザインガバナンスルール |
