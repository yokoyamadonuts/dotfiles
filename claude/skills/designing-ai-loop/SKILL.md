# AI ループ設計（Designing AI Loop）

人間の仕事は「判断基準・評価指標・検証」を設計すること。エージェントは数値ゴールに向けて回る。ループ定義書は **判断基準の文書** であり、夜間基盤やスクリプト群ではない。基盤が要るなら、それはループの最初のタスクとして AI に作らせる。

出典: mizchi「俺のAIプログラミング手法 (2026/10/05)」の「人間の役割を定義する」「考える順番」「/goal と一緒に使う評価指標」。

## 人間が決める 5 つ

| 人間の役割 | 定義書での置き場 |
|-----------|----------------|
| モデルの性能を評価する（無茶振りして限界を知る） | ステップ 3 の試走記録 |
| ループを構築する | ステップ 6 の起動 |
| 評価指標を作る（何を改善し、何を優先するか） | ステップ 2 の指標表 |
| イテレーションを評価する（行動ログを見る） | ステップ 4 の「人間が呼ばれる地点」 |
| テストと CI をチューニングする（優先度・やらないこと） | ステップ 2 の CI 予算 |

## ワークフロー（考える順番）

### 0. 対象を把握する

既存リポなら「現状の構成を読み取って解説して」から入る。読む順は E2E のケース名 → テストコード → 関数シグネチャ。具体実装は読まない（間に合わない）。
一般的でないこだわりや制約は CLAUDE.md / AGENTS.md に「選択肢が複数あるときの判断基準」として書く。ペルソナの名乗りや一般論は書かない。

### 1. 委譲判定

問い: **これは AI に任せられる仕事か。任せられないなら、ブロッカーは何か**（権限 / 情報 / 判断の主観性 / 取り返しのつかなさ）。

結果を 1 行で書く: `任せる` / `条件付きで任せる（条件: …）` / `任せない（ブロッカー: …）`。
「任せない」ならここで終了し、ブロッカーの解消を別タスクにする。

### 2. 完了定義と評価指標

- 完了を数値で言う。数値にできないなら、その仕事はまだ AI に任せられない（ステップ 1 に戻る）。
- **主指標 1 つ＋ガード最大 2 つ**。`references/metrics-catalog.md` から選ぶ。決定的な指標（件数・率・RSS・命令数）を優先し、CI で安定しない壁時計はゲートにしない。
- 各指標に **現在値・目標値・計測コマンド・実行タイミング（毎 PR / 夜間 / 手動）** を付ける。現在値は先に測る。測れないなら「測れるようにする」をループの最初の仕事にする。
- 指標の抜け道を指標側で塞ぐ（例: `eslint --no-inline-config` で `eslint-disable` を数えない、テストの skip・削除・スナップショット更新は ⚠️）。
- トレードオフの優先順位を 1 行で書く（例: テスト成功数 > 最大 RSS > warning 数）。
- CI 予算を書く。指標が増えると CI が伸びる。毎 PR のゲートは何分以内か、何を夜間に回すか、**何をやらないか**。

### 3. 一度やらせて観察する

基盤を作る前に、そのまま 1 回やらせる（対話で 1 イテレーション、または `claude -p "<指示>"`）。

記録するもの: 何ができて何ができなかったか（これがドメイン知識になる）、行動ログで指標を正しく追っていたか、勝手に決めた点。ここで指示と指標を直す。

定義書は試走の前に草稿として書いてよい。試走の記録が空のあいだは草稿であり、ループを起動しない。

### 4. 自動化判定

問い: **人間がつきっきりでなくてよいか = 判断基準を文書化できたか**。

- 残る主観判断を列挙し、それぞれを「人間が呼ばれる地点」にする（朝の PR レビュー、⚠️ 項目の報告）。主観判断が毎イテレーション必要なら、まだループにしない（ユーザーが都度呼び出される）。
- エスカレーションの既定: **DB スキーマ、IaC（Terraform 等）、認証 / 認可、課金、本番設定、削除・公開（npm publish 等）、指標を直接いじれる設定（lint / test / CI の設定、依存の追加）** は人間へ。設定の deny とプロンプトの「着手せず報告」の両方で止める。
- `/compact` が走る前提なら、残すべき判断基準を定義書に書いておく（基準が無いと圧縮で間違った側に倒れる）。

### 5. 失敗を分類する

試走や運用で失敗したら、症状ではなく原因で 3 つに畳む。

| 原因 | 兆候 | 対処 |
|------|------|------|
| コンテキスト不足 | 指示を誤解する、守るべき制約を知らない、同じ失敗を繰り返す | 指示・判断基準・守るべきテストを足す（CLAUDE.md / `.claude/rules` / テスト） |
| 権限不足 | 必要な操作が拒否される、外部に届かない | 付与してよいか検討する。危険なら「人間が代行する地点」にする |
| 性能不足 | 指示も権限も揃っているのに解けない | 記録して寝かせる（半年待つ）。基盤を肥大化させて補わない |

### 6. ループ定義書を書き、起動する

`docs/loops/<name>.md` に下のテンプレートどおり書く（100 行以内が目安）。起動は仕事の形で選ぶ。

| 形 | 起動 |
|----|------|
| 完了条件を満たすまで回す（記事の /goal そのもの。別モデルが毎ターン条件を判定） | `/goal <条件>`。条件は「測れる終了状態＋確認方法＋守る制約」、例: `/goal eslint の warning が 0 件で vitest が exit 0。infra/ は変更しない。or stop after 20 turns` |
| 同じ指示を固定回数まで繰り返す | `/ralph-wiggum:ralph-loop "<指示>" --max-iterations N --completion-promise "<主指標が目標に達した旨>"` |
| 一定間隔で同じコマンド | `/loop <interval> <command>` |
| 多段のワークフロー（計画 → 実装 → レビュー） | `takt-orchestration` |
| 干渉しない複数レーンを並列 | `herdr-swarm` / `superpowers:dispatching-parallel-agents` |

- 進捗の状態は入力 Issue のチェックボックスに持たせる。1 イテレーション = 1 項目 = 1 PR（または 1 コミット）。
- `/goal` の条件と `--completion-promise` は、どちらも主指標の目標到達をそのまま文にする（例: `ESLint warning 数が 0 で、テスト成功数が 418 以上`）。`/goal` は評価モデルが会話に現れた結果だけを見るので、計測コマンドを実行してその出力を会話に出す指示を含める。
- 最初は手動で起動して回す。スケジューラ化（cron / launchd）は成功した後に入力の Issue へ積む。

スクリプト・CI 設定・権限設定が必要なら、それは **ループの最初のタスク** として入力の Issue に積む。定義書には書かない。

## 出力テンプレート（docs/loops/<name>.md）

```markdown
# ループ: acme-cli-lint

## 対象と委譲判定
- 対象: acme-cli（TypeScript CLI、約 25k 行）
- 判定: 条件付きで任せる（条件: ⚠️ 項目は着手せず報告。`infra/` と `scripts/release.sh` は変更禁止）
- 入力: Umbrella Issue #42（exploring-improvements）、docs/quality-bar.md

## 評価指標
| 役割 | 指標 | 現在値 | 目標値 | 計測コマンド | 決定性 | 実行タイミング |
|------|------|--------|--------|-------------|--------|---------------|
| 主 | ESLint warning 数 | 312 | 0 | `eslint . -f json \| jq '[.[].warningCount] \| add'` | 高 | 毎 PR |
| ガード | テスト成功数 | 418 | 減らさない | `vitest run --reporter=json` | 高 | 毎 PR |
| ガード | 最大 RSS（テスト実行） | 1.9 GB | 増やさない | `/usr/bin/time -l pnpm test` | 高 | 夜間 |
- 優先順位: テスト成功数 > 最大 RSS > warning 数
- CI 予算: 毎 PR ゲートは 10 分以内。mutation test は夜間のみ
- やらないこと: カバレッジ目標は置かない（warning 0 を先に）

## 試走の記録
- 2026-10-06: 「ESLint rule `no-unused-vars` の warning を 1 ファイル直して PR」→ できた。rule を指定しないと複数 rule を同時に触った → 指示を「1 PR 1 rule」に修正

## 停止条件
- 主指標が目標に到達、または 10 イテレーション、またはガード違反で破棄したイテレーションが 2 回連続
- completion-promise: "ESLint warning 数が 0 で、テスト成功数が 418 以上"

## 人間が呼ばれる地点とエスカレーション
- 毎朝の PR レビュー（15 分）
- ⚠️ DB スキーマ / IaC / 認証認可 / 課金 / 本番設定 / 削除・公開 → 着手せず報告

## 失敗時の切り分け
- コンテキスト不足 → `.claude/rules` に判断基準を足す / 権限不足 → 代行地点にする / 性能不足 → 記録して寝かせる

## 起動
/goal Issue #42 を上から順に 1 PR 1 rule で処理し、`eslint . -f json | jq '[.[].warningCount] | add'` が 0、`vitest run` の成功数が 418 以上になる。⚠️ の項目は着手せず報告する。or stop after 10 turns
（固定回数で回すなら: /ralph-wiggum:ralph-loop "..." --max-iterations 10 --completion-promise "ESLint warning 数が 0 で、テスト成功数が 418 以上"）
```

## 赤信号（形が崩れている兆候）

| 兆候 | 戻し方 |
|------|-------|
| 1 回も走らせずに夜間基盤（スケジューラ・ゲートスクリプト・権限設定・段階導入計画）を設計している | ステップ 3 に戻る。基盤はループの最初のタスクにする |
| 定義書が数百行になり、付録にスクリプトが並ぶ | 判断基準だけに削る（100 行以内）。スクリプトは入力の Issue へ |
| 指標が 3 つ以上並列で、優先順位が書かれていない | 主 1 つ＋ガード 2 つ。残りは次のループ |
| 壁時計（秒）をゲートにしている | RSS・命令数・件数に言い換える |
| 失敗を症状ごとに 10 件以上列挙している | コンテキスト / 権限 / 性能の 3 分類に畳む |
| 「AI に任せられるか」を問わずに始めている | ステップ 1 の 1 行を書く |
| 主観判断（設計の良し悪し等）を毎イテレーションの合否に使っている | 人間が呼ばれる地点にするか、数値に置き換える |

## 関連スキル

- **exploring-improvements**: 視点で改善点を探し、Umbrella Issue に束ねる。本スキルの入力
- **developing**: `docs/quality-bar.md`（フェーズ別カバレッジ・リスク別必須テスト）は指標の入力
- **plan-first**: 1 回限りの実装計画。繰り返し回すなら本スキル
- `/goal` / `/ralph-wiggum:ralph-loop` / **takt-orchestration** / **herdr-swarm**: 実行ハーネス。定義書を渡す先
- **formal-methods-reconciler**: 並行処理・権限・設定の正しさを指標（反例数）にするとき
- **vcsdd-lite**: Phase 6 の収束シグナルを停止条件に流用できる
