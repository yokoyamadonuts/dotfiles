# Verified Spec-Driven Development (VSDD)

Spec-Driven Development + TDD + Verification-Driven Development を統合したAI協調開発パイプライン。

## 概要

VSDDは3つのパラダイムを**逐次ゲート**として統合する：

1. **Spec-Driven Development (SDD)**: 契約を先に定義。仕様が唯一の真実の源泉
2. **Test-Driven Development (TDD)**: テストが先。Red → Green → Refactor
3. **Verification-Driven Development (VDD)**: 敵対的検証で生き残るまで完成としない

**人間の役割**: 戦略的意思決定者・最終承認者。AIにより役割は**高度化**される（矮小化ではない）。

## ロール定義

| ロール | 担当 | 機能 |
|--------|------|------|
| **Architect** | 人間（開発者） | 戦略的ビジョン、ドメイン専門知識、仕様承認、紛争調停 |
| **Builder** | Claude（メインAI） | 仕様作成、テスト生成、コード実装、リファクタリング、CEG構築 |
| **Adversary** | 別モデル or 別コンテキスト | 容赦なき批判的レビュー。仕様・テスト・実装・CEG整合性すべてを攻撃 |
| **Verifier** | Builderと別コンテキスト or 別モデル | 形式検証ツールのコーディネート、プロパティテスト・ファジング実行管理 |

**認知的多様性**: Adversaryは可能な限りBuilderと異なるモデル/コンテキストを使用する。同じ盲点を避けるため。

## 適用判断

### VSDDを使うべきケース

- 正確性が非交渉（金融、医療、インフラ）
- 長期保守されるコードベース
- セキュリティが主要な関心事
- 複数AIモデルが利用可能

### 軽量に使うケース

プロトタイプやスクリプトにはフルセレモニーは不要。TDD + 簡易的な敵対的レビューだけでも十分。

> **既存 `developing` スキルとの関係**: `developing` はTDDワークフロー。VSDDはそれを含みつつ、仕様駆動・敵対的検証・形式検証を追加した上位パイプライン。

## モード（lean / strict）

VCSDD-lite は2つの運用モードを持つ。Phase 1 開始時に決定し、`docs/vcsdd/<feature>/coherence.json` の `mode` フィールドに記録される。

| モード | 用途 | 厳格度 |
|---|---|---|
| **lean** | プロトタイプ、MVP、個人プロジェクト | Sprint契約・形式検証は選択的 |
| **strict** | 金融・認証・インフラ・長期保守コード | Sprint契約・形式検証・敵対的レビュー全て必須 |

詳細は **references/strict-vs-lean.md** を参照。

## コアワークフロー

### Phase 0 — 品質バーの言語化（Articulating Quality）

**仕様を書く前に「目指す品質」を明文化する。**

> **詳細は `developing` スキルの「品質基準の言語化」セクションを参照。**

VSDD の Phase 1 以降が機能するための **前提条件**。JSTQB FL「早期テスト原則」に基づき、欠陥の混入予防を最上流で行う。

#### 0a: フェーズ別品質定義

プロダクトの成熟度（PoC / MVP / Growth / Mature）を確認し、対応するカバレッジ・エラー処理・パフォーマンス基準を `docs/quality-bar.md` に記載。

#### 0b: リスク評価

開発対象機能のリスクレベル（高/中/低）を判定。Capers Jones の欠陥カバレッジ理論に基づく：
- **高リスク**: 決済、認証、データ削除など → 95%+ カバレッジ、E2E + ファズ必須
- **中リスク**: フォーム、検索など → 80% カバレッジ、Unit + 統合
- **低リスク**: 表示、UI状態 → 50% カバレッジ、Unit のみ

#### 0c: テストスコープの確定

テストピラミッドに従い、Unit / Integration / E2E のテスト責務を明確化。

**Phase 0 完了条件**: `docs/quality-bar.md` が存在し、対象機能のリスクレベルが判定されていること。

### Phase 1 — 仕様結晶化（Spec Crystallization）

**契約が固まるまで何も作らない。アーキテクチャは検証可能性を前提に設計する。**

#### 1a: 振る舞い仕様（Behavioral Specification）

Builderが以下を含む仕様書を作成：

- **振る舞い契約**: 事前条件・事後条件・不変条件で表現
- **インターフェース定義**: 入力型、出力型、エラー型。曖昧さゼロ
- **エッジケースカタログ**: 境界値、退化入力、失敗モードを網羅的に列挙
  - null? 空? 最大サイズ? 負数? Unicode? 並行アクセス?
- **非機能要件**: パフォーマンス上限、メモリ制約、セキュリティ要件

#### 1b: 検証アーキテクチャ（Verification Architecture）

実装設計を確定する**前に**、検証戦略を策定する。

**証明可能プロパティカタログ**:
- どの不変条件・安全性プロパティを**形式的に証明**すべきか特定
- 例: 「この状態機械は無効な状態に到達しない」「このアクセス制御は迂回されない」
- 証明すべきもの（クリティカルパス、セキュリティ境界）とテストで十分なものを区別

**純粋境界マップ（Purity Boundary Map）**:

```
┌─────────────────────────────────────┐
│          Effectful Shell            │
│  (I/O, Network, DB, UI)            │
│                                     │
│  ┌─────────────────────────────┐   │
│  │       Pure Core              │   │
│  │  (決定論的、副作用なし)       │   │
│  │  → 形式検証ツールが推論可能   │   │
│  └─────────────────────────────┘   │
│                                     │
└─────────────────────────────────────┘
```

- **Pure Core**: 決定論的・副作用なしのコアロジック。形式検証の対象
- **Effectful Shell**: I/O、ネットワーク、DB等。テストで検証

> **Phase 1で境界を引く理由**: 副作用がコアロジックに織り込まれたシステムは、Phase 5でどれだけ頑張っても形式検証できない。DBから読んで計算して書き込む一枚岩の関数は検証不能だが、データを受け取り結果を返すだけの純粋関数は検証可能。

**検証ツール選定**:
- 言語と証明対象に基づいてツールを選定
- Rust: Kani / C/C++: CBMC / 分散システム: TLA+ / 汎用: Dafny
- ツール制約は**アーキテクチャ制約**として Phase 1 で反映する

**プロパティ仕様の草案**:
- 可能な範囲でKaniハーネス、Dafny契約、TLA+不変条件を仕様と並行して記述

#### 1c: Coherence Mapping（CoDD核心）

**仕様・テスト・実装・検証の依存関係をCEGに登録する。**

##### frontmatter の必須化

`docs/vcsdd/<feature>/specs/*.md` の冒頭に必ず以下のfrontmatterを付与：

```yaml
---
id: spec:<slug>
type: spec
feature: <feature-name>
coherence:
  depends_on: [...]   # 上流ノード
  satisfies: [...]    # 満たす要件
  verified_by: [...]  # 検証するtest/verify
  beads: [...]        # トレース束
---
```

詳細は **references/coherence.md** を参照。

##### CEG構築

```bash
deno run --allow-read --allow-write \
  ~/.claude/skills/vcsdd-lite/scripts/coherence-scan.ts --feature <feature>
```

`docs/vcsdd/<feature>/coherence.json` が生成される。

##### Phase 1c 完了条件

- 全 spec ファイルに frontmatter が付与されている
- `coherence-scan.ts` が成功（エラーなく完了）
- `coherence-validate.ts` の verdict が `pass` または errors=0 のみ
- 信頼度バンドの green が全 spec の80%以上

#### 1d: 仕様レビューゲート

振る舞い仕様 + 検証アーキテクチャの**両方**を人間とAdversaryがレビュー。

**Adversaryの検査項目**:
- 曖昧な表現（複数解釈が可能な文言）
- 欠落したエッジケース
- 明示されていない暗黙の前提
- 仕様内の矛盾
- テストだけで済ませようとしている本来証明すべきプロパティ
- 純粋境界の違反（Pure Coreと称しているが外部状態に依存）
- 検証ツールのミスマッチ（選択したツールで証明不可能なプロパティ）

**仕様はAdversaryが正当な穴を見つけられなくなるまで反復する。**

### Phase 2 — テストファースト実装（TDD Core）

**Red → Green → Refactor。AIに厳格に強制。**

> **詳細なTDDガイドラインは `developing` スキルを参照。**

#### 2a: テストスイート生成

> **必須前段: `writing-tests` スキルの「テスト観点フレームワーク（QA 6技法）」と「二段階依頼パターン」に従う。**

**二段階で実行する**:

**Step 2a-1: 観点整理（コード生成しない）**

`writing-tests` の QA 6技法に基づき、`docs/vsdd-test-perspective-[feature].md` を作成：

1. **同値分割** - 入力の同値クラス表
2. **境界値分析** - 各境界の off-by-one リスト
3. **デシジョンテーブル** - 条件組み合わせ表
4. **状態遷移テスト** - 状態遷移図と不正遷移リスト
5. **エラー推測** - 過去障害パターン
6. **チェックリスト化** - 機能カテゴリ別チェックリスト

**Step 2a-2: テストコード生成**

観点表に基づき、仕様から直接テストを導出：

| テスト種別 | 対応元 | QA技法 |
|-----------|--------|--------|
| ユニットテスト | 振る舞い契約の各項目 → アサーション | 同値分割 |
| エッジケーステスト | エッジケースカタログ + 境界値リスト | 境界値分析 |
| 統合テスト | モジュール間の相互作用仕様 | デシジョンテーブル |
| 状態遷移テスト | 状態機械仕様 | 状態遷移 |
| エラーパステスト | 失敗モード | エラー推測 |
| プロパティベーステスト | 不変条件（Hypothesis, fast-check, proptest等） | - |

**カバレッジ要求**: Phase 0b で確定したリスクレベルに対応する目標値を満たすこと。

**REDゲート**: すべてのテストが実装なしで**失敗**することを確認。テストが実装なしで通過する場合、テスト自体が疑わしい。

#### 2b: 最小実装

各テストを**1つずつ**通過させる最小コードを書く。

```
1. 次の失敗テストを選ぶ
2. そのテストだけ通す最小コードを書く
3. 全スイートを実行 — 他が壊れていないか確認
4. 繰り返す
```

**Builder への明示的指示**: 「テストを先に書け。実装コードはテストが全て失敗するまで書くな。実装時は各テストを通す最小限のコードのみ書け。」

#### 2c: リファクタリング

全テストがグリーンの後、可読性・パフォーマンス・非機能要件の観点でリファクタリング。

#### 人間チェックポイント

テストスイートと実装が仕様の**精神**と合致しているか確認。AIは契約の文言は守れても、意図を外すことがある。

### Phase 3 — 敵対的精錬（Adversarial Refinement）

**テストを通過したコードが本当の試練に直面する。**

検証済みコード + 仕様 + テストスイートを**新しいコンテキストウィンドウ**のAdversaryに提示。

#### Adversaryのレビュー対象

| 観点 | 内容 |
|------|------|
| 仕様忠実度 | 実装は本当に仕様を満たしているか？テストが誤解をエンコードしていないか？ |
| テスト品質 | テストは主張通りのことをテストしているか？モック過多ではないか？トートロジカルではないか？ |
| コード品質 | プレースホルダ、汎用的エラーハンドリング、隠れた結合、リソースリーク、競合状態 |
| セキュリティ | 入力バリデーション漏れ、インジェクション、認証/認可の前提 |
| 仕様ギャップ | 実装に含まれるが仕様にない振る舞い |

**レビューの原則**:
- **ゼロ寛容**: 「全体的にはいいですが…」の前置きは禁止。すべて具体的な欠陥+場所+修正案
- **コンテキストリセット**: 毎回新しいコンテキスト。蓄積されたgoodwillなし
- **強制否定**: LLMの礼儀正しさフィルターをバイパス。不変条件だけを気にする

### Phase 4 — フィードバック統合ループ

Adversaryの指摘をパイプライン全体にフィードバック：

| 欠陥の種類 | 戻り先 |
|-----------|--------|
| 仕様レベルの欠陥 | → Phase 1（仕様更新、再レビュー） |
| テストレベルの欠陥 | → Phase 2a（テスト修正/追加、失敗確認） |
| 実装レベルの欠陥 | → Phase 2c（リファクタリング、全テスト再実行） |
| 新規エッジケース | → 仕様のエッジケースカタログに追加 → 失敗テスト → 修正 |

**収束するまでループを継続。**

#### 4a: 影響伝播分析（CoDD強化）

Adversaryが仕様レベル欠陥を指摘した場合、修正が他ノードに波及するかをCEGで確認：

```bash
deno run --allow-read \
  ~/.claude/skills/vcsdd-lite/scripts/coherence-impact.ts \
  --feature <feature> --node <changed-node-id> --format md
```

影響範囲に含まれる全ノードを再レビュー対象とする。影響伝播BFSアルゴリズムの詳細は **references/coherence.md** を参照。

### Phase 5 — 形式硬化（Formal Hardening）

Phase 1bで設計した検証アーキテクチャを実装に対して**実行**する。

#### 実行項目

| 項目 | 内容 |
|------|------|
| **証明実行** | Kaniハーネス/Dafny契約/TLA+不変条件を実装に対して実行 |
| **ファズテスト** | AFL++, libFuzzer, cargo-fuzz等でPure Coreを攻撃 |
| **セキュリティハードニング** | Wycheproof（暗号エッジケース）、Semgrep（静的解析） |
| **ミューテーションテスト** | mutmut/Strykerでコードを変異 → テストがキャッチするか確認 |
| **純粋境界監査** | Phase 1bの純粋境界が実装で守られているか最終確認 |

すべての結果に問題があれば Phase 4 にフィードバック。

### Phase 6 — 収束（Convergence）

**4次元すべてが独立して敵対的レビューを生存した時に完了。**

| 次元 | 収束シグナル |
|------|-------------|
| **仕様** | Adversaryの指摘が表現の微修正レベルに留まる |
| **テスト** | Adversaryが意味のある未テストシナリオを見つけられない。ミューテーションテストの殺傷率が高い |
| **実装** | Adversaryがコードに存在しない問題を捏造し始める |
| **検証** | Phase 1bカタログのすべてのプロパティが形式証明を通過。ファザーが何も見つけない。純粋境界が維持 |
| **CEG整合性** | `coherence-validate.ts --strict` が exit code 0、全 spec が confidence: green、bead completeness: full |

**Phase 6 自動チェック**:
```bash
deno run --allow-read --allow-write \
  ~/.claude/skills/vcsdd-lite/scripts/coherence-scan.ts --feature <feature>
deno run --allow-read \
  ~/.claude/skills/vcsdd-lite/scripts/coherence-validate.ts --feature <feature> --strict
```

両方がexit 0で完了し、かつ4次元すべてが独立して敵対的レビューを生存したときに完了。

**Maximum Viable Refinement** 到達 = **Zero-Slop** ソフトウェア。

## トレーサビリティチェーン

VSDDの全成果物は双方向に追跡可能：

```
仕様要件 → 検証プロパティ → テストケース → 実装 → 敵対的レビュー → 形式証明
```

- 「このコード行はなぜ存在するか？」→ 仕様要件まで遡れる
- 「このモジュールはなぜ純粋関数か？」→ Phase 1bの純粋境界マップに遡れる

## コア原則

1. **仕様至上**: 仕様は人間に次ぐ最高権威。テストは仕様に仕え、コードはテストに仕える
2. **検証ファーストアーキテクチャ**: 形式的証明可能性がアーキテクチャを規定する。Pure Core + Effectful Shell
3. **REDの前にGREENなし**: 失敗するテストなしに実装コードを書かない
4. **Anti-Slop バイアス**: 最初の「正しい」バージョンには隠れた負債がある前提。信頼は敵対的生存で獲得
5. **強制否定**: Adversaryは礼儀を持たない。不変条件だけを気にする
6. **コンテキストリセット**: 敵対的レビューは毎回新しいコンテキスト。長期会話の劣化を防ぐ
7. **4次元収束**: 仕様・テスト・実装・形式証明のすべてが独立して敵対的レビューを生存するまで完了しない

## AI オーケストレーション

### Builder への指示テンプレート

```
あなたは厳格なTDD制約下で動作する。
1. テストを先に書け
2. すべてのテストが失敗することを確認するまで実装コードを書くな
3. 実装時は各テストを通す最小限のコードのみ書け
4. テストと実装を同時に書くな
```

### Adversary への指示テンプレート

```
あなたは容赦なきコードレビュアーである。
- 「全体的に良い」の前置きは禁止
- すべての指摘は：具体的な欠陥 + 正確な場所 + 修正案
- 存在しない問題を捏造するな。本物の欠陥だけを指摘せよ
- 仕様・テスト・実装・検証すべてを攻撃対象とせよ
```

### TDD強制のプロンプトエンジニアリング

明示的指示なしでは、AIは自然にテストと実装を同時に書こうとする。必ず制約を明示する。

## 関連スキル

### 品質保証スキル群（必須読み込み）

VSDD は以下の品質保証スキルを**各Phaseで明示的に読み込んで実行する**：

| スキル | 読み込みタイミング | 担う品質保証要素 |
|-------|----------------|-------------|
| **`developing`** | Phase 0全体 / Phase 2 | 品質基準の言語化（フェーズ別品質/リスク評価/テストスコープ）、TDDワークフロー |
| **`writing-tests`** | Phase 2a | テスト観点フレームワーク（QA 6技法）、二段階依頼パターン、言語別テストパターン |
| **`qa-testing`** | Phase 6 後段 | Chrome DevTools MCPによるE2E QA検証（スモーク/クリティカルパス/レスポンシブ/A11y/セキュリティ） |

> **VSDD実行時の挙動**:
> - Phase 0開始時: `developing`の「品質基準の言語化」セクションを必ず参照し、`docs/quality-bar.md`を作成・更新する
> - Phase 2a開始時: `writing-tests`の「テスト観点フレームワーク」と「二段階依頼パターン」を必ず適用する
> - Phase 6完了後: Webプロダクトの場合は`qa-testing`の6フェーズQA検証を実施する

### その他の関連スキル

- **`design-intent`**: 設計意図レビュー（Phase 3の補完として使用可能）
- **`devils-advocate`**: 戦略レベルのストレステスト（Phase 3と相補的）
- **`analyzing-requirements`**: 要件分析（Phase 1の仕様結晶化の入力として使用）
- **`ship-check`**: プロダクトレベルの出荷判断（Phase 6の後に使用）
