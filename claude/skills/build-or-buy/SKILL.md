# Build vs Buy 意思決定スキル

## 概要

「何を作らないかを知ること」がMVP開発で最も重要な能力。このスキルは、特定の機能について自作（Build）と外部サービス/ライブラリ利用（Buy）を構造的に比較し、意思決定ドキュメントを生成する。

## ユースケース

- 認証を自作するか Auth0/Clerk を使うか
- 検索機能を自前実装するか Algolia/Meilisearch を使うか
- 決済処理を Stripe に任せるか自作するか
- メール送信を自前 SMTP か SendGrid/Resend か
- ファイルストレージを自前 S3 管理か Uploadthing/Cloudinary か
- ORM を使うか生 SQL か

### ステップ2: 選択肢の列挙

自作（Build）と Buy 候補を2-3件リストアップする。

**Buy候補のリサーチ方法**:
- 既知の定番サービスをリスト
- 必要なら `competitive-research` スキルと連携してBuy候補を詳細比較

```
Build: 自前実装
Buy候補1: [サービスA] - 最も人気
Buy候補2: [サービスB] - コスト重視
Buy候補3: [OSS C] - セルフホスト可能
```

### ステップ3: 評価マトリクスの作成

以下の6軸で各選択肢を評価する：

| 評価軸 | Build | Buy候補1 | Buy候補2 |
|--------|-------|----------|----------|
| **出荷速度** | 実装にかかる期間 | 統合にかかる期間 | 統合にかかる期間 |
| **初期コスト** | 開発工数 | 月額/従量課金 | 月額/従量課金 |
| **カスタマイズ性** | 完全な自由度 | API/設定の範囲 | API/設定の範囲 |
| **保守負担** | 自分でバグ修正・更新 | プロバイダが管理 | プロバイダが管理 |
| **ロックインリスク** | なし | データ移行の容易さ | データ移行の容易さ |
| **スケーラビリティ** | 自分で設計 | プロバイダの実績 | プロバイダの実績 |

各セルには具体的な数値・根拠を記入する。曖昧な表現（「良い」「悪い」）は使わない。

### ステップ4: 隠れコスト分析

Build vs Buy それぞれに隠れコストが存在する。明示的に洗い出す：

**Buildの隠れコスト**:
- セキュリティパッチの継続的な適用
- エッジケースの発見と対応（本番で初めて発覚するバグ）
- ドキュメント作成・新メンバーへの引き継ぎ
- 機会コスト（その時間でプロダクトのコア機能を作れた）

**Buyの隠れコスト**:
- ユーザー数増加時の従量課金スケール
- プロバイダ障害時のダウンタイム（自分でコントロール不可）
- API変更・非推奨化への追従
- サービス終了リスク
- データのポータビリティ制約

### ステップ5: リスク評価

最悪のシナリオを想定する：

**Buildを選んだ場合の最悪シナリオ**:
- 想定の3倍の開発期間
- 本番でセキュリティインシデント
- 開発者が退職し、保守不能に

**Buyを選んだ場合の最悪シナリオ**:
- サービスが値上げ/終了
- 必要な機能がサポートされない
- データ移行が困難
- 障害発生時に何もできない

### ステップ6: 意思決定と再検討条件

明確な推奨を出す。ただし、将来の再検討トリガーも定義する：

```
推奨: [Build or Buy候補X]
理由: [1-2文の根拠]

再検討トリガー:
- [条件1が変わったら再評価]
- [条件2に達したら再評価]
```

## 第3の選択肢: BYOK（Bring Your Own Key）

AI機能を持つプロダクトの場合、Build/Buy以外に**BYOK**という選択肢がある（Tony Dinh方式）。

ユーザーが自分のAPIキー（OpenAI、Anthropic等）を持ち込むモデル：

| 観点 | Build | Buy（API代行） | BYOK |
|------|-------|---------------|------|
| インフラコスト | 高（自社GPU/API） | 中（マージンを乗せる） | **ゼロ** |
| UX | 最高 | 良い | やや複雑（APIキー設定） |
| スケーリング | 自社負担 | コスト増大 | **ユーザー負担** |
| 利益率 | 低 | 中 | **最高** |
| ターゲット | 一般ユーザー | 一般ユーザー | 技術者・パワーユーザー |

**BYOKが有利な場合**:
- AI APIコストがMRRの20%を超える
- ターゲットが技術者（APIキー管理に抵抗がない）
- インディー開発者で、サーバーコストを最小化したい

**BYOKが不利な場合**:
- 一般消費者向けプロダクト
- APIキーの概念が理解されないターゲット
- UXの簡潔さが最優先

## 判定のヒューリスティクス

以下は一般的な傾向。プロジェクト文脈で常に再評価すること：

**Buyが有利な場合が多い**:
- 認証・認可（セキュリティリスクが高すぎる）
- 決済処理（PCI DSS準拠が大変）
- メール配信（到達率の最適化が難しい）
- エラートラッキング（Sentry等が圧倒的に成熟）
- アナリティクス（PostHog等のコスパが良い）

**Buildが有利な場合が多い**:
- プロダクトのコア差別化要素
- 非常にシンプルな機能（外部サービスが過剰）
- オフライン/エアギャップ環境
- 極端なカスタマイズが必要

**判断が分かれやすい**:
- 検索機能（規模とクエリ複雑性による）
- リアルタイム通信（WebSocket vs Pusher等）
- ファイルアップロード（要件の複雑さによる）
- CMS（ヘッドレスCMS vs 自前）

**インディー開発者のバイアスに注意**:
- 「自分で作った方が楽しい」→ 楽しさは判断基準ではない。速度が基準
- 「外部サービスの月額が高い」→ 自分の開発時間のコストを忘れている
- 「いつかは自作に移行する」→ 「いつか」は来ない。今の判断に集中
- 「BYOKにすればタダ」→ UXの犠牲を定量化せよ
