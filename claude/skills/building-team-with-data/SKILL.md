# データ駆動構築スキル（poke-cli連携）

## 概要

`building-meta-coverage` スキルの構築理論を、poke-cliのデータ（メタ使用率・ダメージ計算・弱点分析・バトルシミュ）で裏付けながら実行するワークフロー。理論だけでなく数値的根拠のある構築案を生成する。

**前提**: poke-cliバイナリが `/Volumes/Partition_Case_Sensitive/poke-cli/poke-cli` にあること。

```bash
POKE=/Volumes/Partition_Case_Sensitive/poke-cli/poke-cli
```

## ワークフロー

最初にルールを確認し、メタデータを取得する:

```javascript
AskUserQuestion({
  questions: [{
    question: "どのルールで構築を組みますか？",
    header: "ルール",
    options: [
      { label: "シングルバトル（ランクマッチ）", description: "BSS形式" },
      { label: "ダブルバトル（VGC）", description: "VGC公式大会形式" },
      { label: "ダブルバトル（ランクマッチ）", description: "ランクマダブル" }
    ],
    multiSelect: false
  }]
})
```

---

### Step 1: メタデータ取得 — 環境トップの特定

```bash
# メタデータ取得（初回 or 7日以上経過時）
$POKE meta fetch --rule singles    # or doubles

# 使用率上位20体を取得
$POKE meta usage --rule singles --limit 20 --output json
```

JSON出力から以下を抽出する:
- **使用率トップ5** → building-meta-coverageの「環境トップ」
- **各ポケモンの人気技・持ち物・テラスタイプ** → テンプレ型の把握（型ずらしの基準）
- **よく組まれるチームメイト** → 多い並びの把握

このデータを元にユーザーに環境認識を提示し、構築の方向性を相談する。

---

### Step 2: 軸ポケモンの決定と性質分析

ユーザーと相談して軸ポケモンを1体決めたら、データで性質を確認:

```bash
# 種族値・タイプ・特性の確認
$POKE pokemon [軸ポケモン] --output json

# メタでの採用率・人気型の確認（Step 1のデータから該当ポケモンを抽出）
# → 技採用率、持ち物採用率、性格採用率、テラスタイプ採用率
```

**シングルの場合**: building-meta-coverageのPart 1に従い、全対応枠としての適性を評価する。トップ5への対応マトリクスを理論＋データで埋める。

**ダブルの場合**: Part 2のキヌガワ式D-2に従い、理想の動き・必要なサポートを分析する。

---

### Step 3: レギュレーション適合確認

```bash
# 使用可能ポケモンの確認
$POKE regulation pokemon --reg vgc2025-reg-g --output json  # VGCの場合
$POKE regulation pokemon --reg bss-reg-g --output json      # BSSの場合
```

候補ポケモンが allowed / restricted / banned のいずれかを確認。restricted枠の使用数が上限を超えないか検証する。

---

### Step 4: 取り巻き構築 — 攻め受け補完の検証

候補ポケモンを追加するたびに弱点分析を実行:

```bash
# 現在の構築メンバーの弱点分析
$POKE team analyze --pokemon [ポケモン1],[ポケモン2],[ポケモン3] --output json
```

JSON出力の確認ポイント:
- `severity: "high"` の弱点タイプがないか
- `4x` 弱点が集中していないか
- 全体技（地震・熱風・なだれ等）への一貫が切れているか（ダブル）
- speed_tiers で上から殴れるポケモンがいるか

**6体揃うまで「候補追加 → analyze → 評価」を繰り返す。**

building-meta-coverageの理論に基づく判断:
- **シングル**: 崩し枠A・Bが両方入っているか。全対応枠のカバー率は十分か。
- **ダブル**: 2匹軸が成立しているか。キヌガワ式のD-3（攻め補完）D-4（受け補完）を満たすか。

---

### Step 5: ダメージ計算 — 理論の数値検証

構築の核となる対面でダメージ計算を実行し、理論が数値的に成立するか確認する。

```bash
# 全対応枠 vs トップメタの各対面
$POKE damage calc \
  --attacker [全対応枠] \
  --attacker-evs "252atk" \
  --attacker-nature [性格] \
  --attacker-item [持ち物] \
  --move [技] \
  --defender [トップメタ] \
  --defender-evs "252hp,4def" \
  --output json

# 崩し枠 vs 受けポケモンの対面
$POKE damage calc \
  --attacker [崩し枠A] \
  --move [崩し技] \
  --defender [仮想敵] \
  --output json
```

確認する対面（最低限）:
- 全対応枠 vs トップ4〜5の各ポケモン
- 崩し枠A vs 崩し枠Aの仮想敵
- 崩し枠B vs 崩し枠Bの仮想敵（Aが通らない相手）
- 相手のトップメタのメイン技 vs こちらのクッション枠（被ダメ）

結果の判定基準:
- 確定1発（OHKO）が取れるか
- 確定2発以内で落とせるか
- クッション枠が2発耐えるか

---

### Step 7: 選出パターンの策定

building-meta-coverageのPart 3（選出論）に従い、主要な相手構築に対する選出パターンを策定する。

各選出パターンについて:
1. 初手が4匹以上に有利か確認（ダメージ計算で裏付け）
2. 3体で6体を見れるかチェック（弱点分析で裏付け）
3. テラス先が競合していないか確認

---

### Step 8: バトルシミュレーションによる立ち回り確立

環境のメタ構築パターンごとにサブエージェントを並列起動し、それぞれ複数回対戦して立ち回りを確立する。

#### 8-1. 仮想敵チームの準備

Step 1のメタデータから、環境で多い構築パターンを3〜5つ特定する:

```markdown
| パターン | 代表的な並び | 特徴 |
|---------|-----------|------|
| 対面構築 | [ポケモンA/B/C/D/E/F] | 高速高火力、タスキ・スカーフ多め |
| サイクル構築 | [ポケモンA/B/C/D/E/F] | クッション＋崩し、再生技持ち |
| 受けループ | [ポケモンA/B/C/D/E/F] | 高耐久、毒・宿り木で削る |
| 積み展開 | [ポケモンA/B/C/D/E/F] | 壁＋積みエース |
| 天候/トリル | [ポケモンA/B/C/D/E/F] | 始動要員＋エース |
```

各仮想敵チームは `meta usage` の使用率上位の技・持ち物・性格・テラスタイプで構成する。`team export --with-meta` でShowdown形式を生成し、packed formatに変換して使用する。

#### 8-2. 不完全情報ルール（実戦準拠）

人間同士の対戦と同じ条件でシミュレーションするため、以下のルールを厳守する:

**見せ合い画面で分かること（= 使ってよい情報）:**
- 相手のパーティの6体のポケモン名のみ

**見せ合い画面で分からないこと（= 使ってはいけない情報）:**
- 相手の選出（どの3-4体を出すか）
- 相手の技構成
- 相手の持ち物
- 相手の努力値配分・性格
- 相手のテラスタイプ

**選出・行動選択のルール:**
- P1（提案構築）の選出は、相手のポケモン名6体だけを見て決める。building-meta-coverageのPart 3（選出論）に従い、刺さり判断→絶対出す/出さない→初手4匹以上有利の手順で決定する
- 各ターンの行動選択は、その時点で判明している情報（場に出ているポケモン・これまでに見えた技・発動した特性・持ち物の示唆）のみに基づいて行う
- 「相手がこの技を持っているはず」という推測は、メタデータの使用率（Step 1）に基づく確率的判断として行ってよいが、確定情報としては扱わない
- 相手のテラスタイプは対戦中に切られるまで不明として扱う

**P2（仮想敵）の行動:**
- P2も独立した判断で行動する。P1の構築の詳細（技・持ち物・EV・テラス）は知らない前提で動かす
- P2の選出も同様に、P1のポケモン名6体だけを見て決める
- P2はメタデータ上の標準的な立ち回り（使用率の高い技を優先して打つ等）で行動する

#### 8-3. 並列サブエージェントによる対戦検証

各メタ構築パターンに対して1つのサブエージェントを起動し、並列で対戦・分析・調整を行う:

```javascript
// 全パターンを並列で同時実行
Agent({
  description: "Battle vs 対面構築",
  prompt: `ポケモン対戦のバトルシミュレーション検証を行ってください。

## あなたの担当
「対面構築」パターンとの対戦検証

## 提案構築（P1）
[構築のShowdown packed format]

## 仮想敵（P2）: 対面構築
[仮想敵のShowdown packed format]

## P1が見せ合いで知れる情報
相手のポケモン名6体: [ポケモンA], [ポケモンB], [ポケモンC], [ポケモンD], [ポケモンE], [ポケモンF]
※相手の技・持ち物・EV・テラスは不明

## poke-cliパス
POKE=/Volumes/Partition_Case_Sensitive/poke-cli/poke-cli

## 不完全情報ルール（厳守）
あなたは両プレイヤーの行動を決定しますが、以下を厳守してください:
- P1の選出・行動決定時: P2の技・持ち物・EV・テラスタイプを参照してはいけない。
  相手のポケモン名と、対戦中に実際に見えた情報のみ使用すること。
- P2の選出・行動決定時: P1の技・持ち物・EV・テラスタイプを参照してはいけない。
  P1のポケモン名と、対戦中に実際に見えた情報のみ使用すること。
- メタデータの使用率に基づく推測（「このポケモンは○○を持っていることが多い」）は
  確率的判断として許容するが、確定情報として扱わないこと。
- 各ターンで「なぜこの行動を選んだか」を1文でメモすること（読み・安定行動・ケア等）。

## 手順
1. P1の選出を決める（相手のポケモン名6体のみを見て判断）
2. P2の選出を決める（P1のポケモン名6体のみを見て判断）
3. $POKE battle run でバトルを実行する。各ターンで両者の行動を
   その時点の既知情報だけに基づいて決定する
4. バトルログを分析する:
   - P1の選出は相手のポケモン名だけで判断して適切だったか
   - 対戦中の「読み」は合理的だったか（結果論ではなく判断過程で評価）
   - 不利対面での立ち回りオプションはあったか
5. 問題があれば技構成・持ち物・努力値を微調整する:
   - $POKE damage calc で調整後のダメージを確認
   - 調整理由は「相手の○○が見えてから判断できる範囲」に限定すること
6. 調整後に再度バトルを実行する（選出も改めてポケモン名のみから再判断）
7. 最低3回、安定するまで繰り返す

## 最終レポート形式

### vs 対面構築: 結果
- 戦績: X勝Y敗（全Z戦）
- 推奨選出: [先発] / [裏] / [裏]
  - 選出根拠: [相手の6体のうち何を見てこの3体にしたか]
- 推奨テラス先: [ポケモン名] → [テラスタイプ]
  - テラス判断タイミング: [どの場面で切るべきか]
- 立ち回り方針: [1文で要約]
- ターン別の読みポイント:
  - [初手: ○○が来たら△△、□□が来たら××]
  - [中盤: 相手のテラスが見えたら○○に切り替え]
- 調整箇所: [変更した技・持ち物・EVがあれば記載]
- 注意点: [このパターン特有の負け筋・ケアすべき動き]
`,
  subagent_type: "general-purpose"
})

// 同時に他のパターンも並列起動（同一メッセージで全て呼び出すこと）
Agent({ description: "Battle vs サイクル構築", prompt: `（同様）...` })
Agent({ description: "Battle vs 受けループ",  prompt: `（同様）...` })
Agent({ description: "Battle vs 積み展開",    prompt: `（同様）...` })
Agent({ description: "Battle vs 天候/トリル",  prompt: `（同様）...` })
```

**重要**: 全パターンを**1つのメッセージで同時に**Agent呼び出しすること。順番に実行しない。

#### 8-4. 結果の統合と最終調整

全サブエージェントの結果を統合し、以下を作成する:

```markdown
## バトルシミュレーション結果

| 相手パターン | 戦績 | 推奨選出 | 選出根拠 | テラス先 | 立ち回り方針 |
|------------|------|---------|---------|---------|------------|
| 対面構築    | 3-0  | A/B/C   | 相手にX,Yがいるため | A→鋼    | 初手Aで制圧 |
| サイクル    | 2-1  | A/D/E   | Zが重いため崩し優先 | D→水    | Dで崩してAで詰め |
| ...        | ...  | ...     | ...     | ...     | ...        |

### 読みポイント集（実戦メモ）
- vs 対面構築: 初手○○が来たら△△安定、□□が来たらテラス温存して引き
- vs サイクル: 中盤に相手の××が見えたら崩し枠に切り替え
- vs 受けループ: テラスは相手の毒技を確認してから切る
- ...

### 調整サマリー
- [サブエージェントが提案した調整を集約]
- 調整が競合する場合は遭遇率が高いパターンを優先

### 最終選出パターン表
[building-meta-coverageの選出パターン表を、シミュ結果で更新]
```

調整が発生した場合は Step 5（ダメージ計算）と Step 6（構築保存）を再実行して反映する。
