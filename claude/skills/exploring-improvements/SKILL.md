# 探索的改善（Exploring Improvements）

エージェントは丸投げしても十分に探せる。足りないのは **視点**（誰にとって・何の数値が大事か）と、発見を **1 本の Umbrella Issue** に束ねてループへ渡す出口である。本スキルは探索そのものより、入口（視点と指標）と出口（Issue の形）を固定する。

出典: mizchi「俺のAIプログラミング手法 (2026/10/05)」探索的改善の節。

## 原則

1. **視点が先**: 「誰にとって・何の数値が大事か」を決めてから探す。数値が改善の理由になる。
2. **探索は読み取り専用**: 修正はループ（`designing-ai-loop` → `ralph-loop` / `takt`）で行う。計装が必要なら spike ブランチで、マージしない。
3. **根拠の無い項目は本文に入れない**: `path:line`・計測値・再現手順のどれも無いものは「未検証」節へ。
4. **出力は Umbrella Issue 1 本**: 1 回の探索 = 1 視点 = 1 Issue。個別 Issue や PR はループが切る。
5. **専門内は精査、専門外はレビューを外に出す**: 自分の領域は抜き取りで `path:line` を再確認し、外の領域はその領域の人に渡す。

## ワークフロー

### 1. 視点と指標を宣言する

探索を始める前に、次の 3 行を書く。これが Issue の冒頭にもなる。

```
視点: <カタログの 1 行>
誰にとって / 大事な数値: <人> / <指標（現在値 or 計測方法）>
安全境界: <触らないもの・実行環境>
```

| 視点 | 誰にとって | 大事な数値 | 典型プロンプト | 安全境界 |
|------|-----------|-----------|--------------|---------|
| SRE / 可観測性 | オンコール担当 | p95 レイテンシ、エラー率、trace の無い経路数 | 「SRE 視点でテレメトリを計装して。RED メトリクスと trace が欠けている経路を列挙」 | 本番は変更しない。計装は spike ブランチ |
| セキュリティ（攻撃側） | 攻撃者になったつもりで | 未認可で到達できる経路数、既知脆弱性数 | 「攻撃側としてチェックリストを作り、localhost に閉じてペネトレーションして」 | Docker / サンドボックス必須。localhost 限定。外部送信禁止 |
| パフォーマンス / DB | ユーザー、インフラ費 | p95、リクエストあたりクエリ数、RSS | 「データベースに対する N+1 を見つけて候補を列挙」 | 計測はローカル compose 環境で |
| 保守性 | 次に触る開発者 | 循環的複雑度、重複率、lint warning 数、ユニットテストの無いパッケージ数、mutation kill 率 | 「テストを壊さない範囲でリファクタ候補を列挙」 | 変更しない。候補と根拠だけ |
| 最新研究との比較 | 設計者 | 採用候補数（出典 URL 付き） | 「現在の実装と最新の研究を比較して、参考になるものを列挙」 | 出典の無い主張は書かない |
| 依存関係 | 保守者 | 脆弱な依存数、EOL 数、更新遅延 | 「依存の脆弱性と EOL を棚卸しして」 | lockfile は変更しない |
| DX / CI | 開発者 | CI 所要時間、flaky 率 | 「CI を短くできる箇所と flaky なテストを列挙」 | CI 設定は変更しない |

視点は 1 回の探索で 1 つ（多くても 2 つ）。複数欲しければ別の探索として実行し、Issue も分ける。不満が複数の視点にまたがるときは、他の視点の現在値を測れるようにする視点（SRE / 可観測性）を先に回す。

### 2. 安全境界を決める

- 本番に触らない。書き込まない。外部へ送信しない。
- 自信の無い操作（攻撃系・負荷系・大量クエリ）は Docker か適切なサンドボックスで実行する。
- エージェントに渡す前文（探索プロンプトの先頭に付ける）:

```
あなたは <視点> の立場で <対象> を探索する。目的は <大事な数値> の改善候補を見つけること。
禁止: ファイルの変更、git の書き込み、本番環境への接続、外部へのデータ送信。
根拠: すべての発見に path:line か計測値か再現手順を付ける。無いものは「未検証」として分けて報告する。
出力: 下の発見ログの列で表にする。該当なしも「該当なし」と報告する。
```

### 3. 探索する

視点・指標・安全境界・出力形式を付けて丸投げする。並列にするなら、干渉しない領域（ルータ / DB / 外部呼び出し / 運用設定など）で subagent を分ける（`superpowers:dispatching-parallel-agents` / `herdr-swarm`）。発見ログはスクラッチ領域に置いてコミットせず、正本は Issue 本文にする。

発見ログの列（1 行 1 発見）:

| 列 | 内容 |
|----|------|
| 場所 | `path:line` または設定キー |
| 症状 | 何が起きるか（事実） |
| 影響 | 誰に・どの数値にどう効くか |
| 指標 | 現在値、無ければ計測コマンド |
| 修正案 | 1 PR で閉じる粒度の案 |
| 危険 | DB スキーマ / IaC / 認証認可 / 課金 / 削除・公開 のいずれかに触るなら ⚠️ |
| 確証度 | 計測済 / 静的読み / 推測 |

### 4. 精査する

- 専門内: 発見の 2 割を抜き取り、`path:line` と数値を自分で再確認する（捏造防止）。
- 専門外: その領域のレビューを依頼する。OSS や他チームの repo なら相手の流儀に合わせる（上流スキル `maintainer-persona`: `npx skills add mizchi/skills --skill maintainer-persona`）。
- 確証度が「推測」のままの項目は「未検証」節へ移す。

### 5. Umbrella Issue にまとめる

既存 Issue との重複を確認してから 1 本起票する。

```bash
gh issue list --state all --search "<キーワード>" --limit 50
gh issue create --title "[探索] <視点>: <対象>" --body-file umbrella.md --label exploration
```

本文は下の出力テンプレートに従う。発見は優先順に並べ、上から順にループが処理できる粒度（1 項目 = 1 PR）にする。

- 優先度 = 影響（1-3）× 確証度（計測済 3 / 静的読み 2。推測は未検証節へ）÷ 工数（1-3）。同点は影響する経路や利用者の数が多い順。
- Issue の骨組み（視点と指標・安全境界・未検証・やらないこと・受け渡し）は探索前に書いてよい。発見節だけは探索後に転記する。既知の不満は計測手順を付けて未検証節に置く。
- `exploration` ラベルが無ければ `gh label create exploration --description "探索的改善の Umbrella Issue"` で作る。

### 6. ループへ渡す

Issue 番号を `designing-ai-loop` に渡し、指標の現在値・目標値・停止条件・エスカレーションを `docs/loops/<name>.md` に書く。実行は `/goal` / `ralph-loop` / `takt` / `herdr-swarm`。⚠️ の項目はループに着手させず、人間がレビューする。

## 出力テンプレート（Umbrella Issue）

```markdown
# [探索] SRE 視点: acme-api

## 視点と指標
- 視点: SRE / 可観測性
- 誰にとって / 大事な数値: オンコール担当 / p95 レイテンシ（現在 未計測: `<計測コマンド>`）、trace の無い経路数（現在 12）
- 安全境界: 本番不変更。計測は compose 環境。spike ブランチはマージしない

## 発見（優先順。上から順にループで処理する）
- [ ] **/orders の一覧でクエリが N+1** — `internal/handler/orders.go:88` / 1 リクエストで 1+N 回の SELECT / p95 に直結 / 現在 41 クエリ（20 件取得時） / `sqlc` で JOIN に寄せる / 確証度: 計測済
- [ ] **trace が /auth 配下に無い** — `internal/router.go:40` / otelhttp が未適用 / 障害時に追えない / 経路数 4 / ミドルウェア追加 / 確証度: 静的読み
- [ ] ⚠️ **セッションテーブルに index が無い** — `migrations/0007.sql` / フルスキャン / p95 / `EXPLAIN` で確認済 / index 追加（DB スキーマ変更のため人間がレビュー） / 確証度: 計測済

## 未検証（根拠が揃うまで着手しない）
- 認可判定がハンドラごとに重複している疑い — `chi.Walk` でルート一覧を取り、判定箇所を表にして確認する

## やらないこと
- トレースバックエンドの選定（別 Issue）

## ループへの受け渡し
- 停止条件: trace の無い経路数 0、/orders の p95 が 300ms 以下（`docs/loops/acme-api-sre.md`）
- 起動: `/goal Issue #<N> の発見を上から順に 1 項目 1 PR で処理し、全項目がチェック済みになる。⚠️ の項目は着手せず報告する。or stop after 10 turns`
```

## 赤信号（形が崩れている兆候）

| 兆候 | 戻し方 |
|------|-------|
| 探索の前に発見節が埋まっている、または個別 Issue の草案が並んでいる | 発見節は発見ログから転記する。「既知の不満」は視点と指標に変換し、未検証節に置く |
| Issue が複数本・数日がかりの計画になっている | 1 探索 = 1 視点 = 1 Umbrella Issue。個別 Issue はループが切る |
| 視点に「大事な数値」が無い | 数値の無い視点は改善の理由を作れない。指標を 1 つ決めてから探す |
| 探索中にコードを直し始めている | 探索は読み取り専用。修正はループで |
| 人間の着手順で終わり、ループへの受け渡しが無い | 「ループへの受け渡し」節を埋める。停止条件と起動コマンドまで書く |
| ⚠️ の項目がループの処理対象に混ざっている | 危険フラグの項目は人間レビューに分ける |

## 関連スキル

- **designing-ai-loop**: Umbrella Issue を受け取り、指標・停止条件・エスカレーションを決めてループを起動する
- **ship-check** / **qa-testing**: リリース判定の監査。探索ではなく合否判定に使う
- **`/techdebt`**: 重複・デッドコードの機械検出。保守性視点の探索の道具として併用する
- **formal-methods-reconciler**: 並行処理・権限・設定の整合性が疑われたら、発見を形式モデルと反例テストに落とす
- **herdr-swarm** / **superpowers:dispatching-parallel-agents**: 視点ごとの並列探索
