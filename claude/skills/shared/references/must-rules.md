# MUSTルール リファレンス

要件分析（analyzing-requirements）とタスク分解（planning-tasks）で前提とする開発規律。
方法論の詳細は各SSOTを参照し、ここでは計画に影響する制約のみを示す。

## テスト駆動開発（TDD）

プロダクションコードはTDD（RED→GREEN→REFACTOR）で書くことを前提にタスクを分解する。

- 各機能のタスクは `[RED] テスト作成` → `[GREEN] 実装` → `[REFACTOR] 改善` の3点セットで構成する
- バグ修正は「バグを再現する失敗テストを先に書く」タスクから始める
- テストの優先順位はテスティングトロフィー（ユニット多数 → 統合 → E2E最小限）

詳細なサイクル定義・設計原則・カバレッジ基準は `developing` スキルがSSOT。
例外（プロトタイプ・収益前プロダクトでのVibe Coding Mode）も `developing` スキルの基準に従う。

## Tidy First（構造変更と動作変更の分離）

すべての変更を2種類に分け、同じコミットに混ぜない:

1. **構造的変更**: 動作を変えない再配置（リネーム・抽出・移動・フォーマット）。変更前後でテストを実行して動作不変を検証する
2. **動作的変更**: 機能追加・バグ修正・ビジネスロジック変更。失敗するテストが先行する

両方が必要な場合は構造的変更を先に行う。
コミットメッセージは `[STRUCTURAL]` / `[BEHAVIORAL]` プレフィックスで種別を明示する。

## コミット規律

- テスト・リンターが通った、単一の論理的作業単位のみコミットする
- 大きく頻度の低いコミットより、小さく頻繁なコミットを優先する
- 形式の詳細は `claude/rules/common/git-workflow.md` を参照

## 作業サイクル

- タスクは一度に1つずつ、アトミックでテスト可能な単位で進める
- 各タスク完了後にテスト・lint・formatを実行する
- フェーズ完了時はユーザーの承認を待ってから次に進む
