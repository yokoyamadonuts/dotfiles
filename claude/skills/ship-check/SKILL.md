# リリース前プロダクト品質監査スキル

## 概要

コードレベルの品質（lint/test/build）ではなく、プロダクトレベルの品質を監査する。ユーザーが実際に触ったときの体験、パフォーマンス、セキュリティ基礎、可観測性が整っているかをチェックし、出荷可否を判定する。

## ユースケース

- MVP の初回リリース前チェック
- 新機能リリース前の品質確認
- ホットフィックス後の影響範囲確認
- 定期的なプロダクト健康診断

### ステップ1.5: 収益化バリデーション（初回リリース時必須）

初回リリース時、プロダクトレベルの品質に加えて**収益化の準備**を確認する。

#### 支払いフロー確認

```
チェック項目:
- [ ] Stripe（または決済サービス）が統合されているか
- [ ] 価格ページが存在し、明確な価格が表示されているか
- [ ] テスト決済が正常に完了するか
- [ ] サブスクリプションの場合、キャンセルフローが機能するか
- [ ] 決済成功後のアクセス権限付与が正常か
```

**検出方法**:

```bash
# Stripe統合の検出
rg "stripe|STRIPE" --type ts --type js --type env
# 価格ページの検出
rg "pricing|price|plan" --type tsx --type jsx --type ts -i
```

#### プラットフォーム依存リスク

単一プラットフォームへの過度な依存を検出する：

```
チェック項目:
- [ ] 収益の50%以上が単一プラットフォーム（App Store、Google Play等）に依存していないか
- [ ] 顧客データ（メールアドレス等）を自社で所有しているか
- [ ] プラットフォームのポリシー変更で収益が消えるリスクはないか
- [ ] プラットフォーム移行計画があるか（ウェブ版等）
```

**判定基準**:
- **FAIL**: 収益100%が単一プラットフォーム依存 + 移行計画なし
- **WARN**: 収益50%以上が単一プラットフォーム依存
- **PASS**: ウェブファースト or 複数チャネルで配信

### ステップ2: UX監査

ユーザーが「迷う」「つまずく」ポイントを検出する。

#### 2-1: 空の状態（Empty States）

データがない状態のUIを確認する：

```
チェック項目:
- [ ] 初回ログイン時に何も表示されない画面がないか
- [ ] リスト/テーブルが空のとき、次のアクションが明示されているか
- [ ] 検索結果が0件のとき、適切なメッセージがあるか
- [ ] エラー発生時にユーザーが次にすべきことが分かるか
```

**検出方法**: コードベースから空状態の処理を検索

```bash
# 空の状態の処理を検索
rg "empty|no.?data|no.?results|no.?items|length === 0|\.length\))" --type ts --type tsx
# ローディング状態の検索
rg "loading|skeleton|spinner|isLoading" --type ts --type tsx
```

#### 2-2: オンボーディング

```
チェック項目:
- [ ] 新規ユーザーが最初にすべきアクションが明確か
- [ ] 初回利用時のガイド/ツールチップがあるか
- [ ] セットアップウィザードが必要な場合、実装されているか
```

#### 2-3: エラーUX

```
チェック項目:
- [ ] フォームバリデーションエラーがフィールド横に表示されるか
- [ ] ネットワークエラー時にリトライ手段があるか
- [ ] 404ページにホームへの導線があるか
- [ ] エラーメッセージが技術用語でなくユーザー向けか
```

### ステップ3: パフォーマンス監査

#### 3-1: 画像最適化

```
チェック項目:
- [ ] next/image 等の最適化コンポーネントを使用しているか
- [ ] 適切なサイズ指定（width/height）があるか
- [ ] WebP/AVIF等の次世代フォーマットを使用しているか
- [ ] 遅延読み込み（lazy loading）が適用されているか
```

**検出方法**:

```bash
# 生のimg タグを検索
rg "<img " --type html --type tsx --type jsx
# next/image の使用確認
rg "from ['\"]next/image['\"]" --type ts --type tsx
```

#### 3-2: バンドルサイズ

```
チェック項目:
- [ ] 不要な大型ライブラリが含まれていないか
- [ ] ツリーシェイキングが有効か（barrel exportの確認）
- [ ] 動的インポート（code splitting）が適切に使用されているか
```

#### 3-3: クライアントサイド過多（Next.js/RSC向け）

```
チェック項目:
- [ ] "use client" が不必要に多用されていないか
- [ ] Server Componentで十分なコンポーネントがClient化されていないか
- [ ] データフェッチがクライアントサイドに偏っていないか
```

**検出方法**:

```bash
# "use client" の使用箇所を列挙
rg "\"use client\"" --type ts --type tsx -c
```

### ステップ4: セキュリティ簡易スキャン

本格的なセキュリティ監査ではなく、よくある見落としを検出する。

#### 4-1: ハードコードされた秘密鍵

```bash
# APIキー・シークレットのハードコードを検索
rg "(api.?key|secret|password|token|credential).*[=:].*['\"][a-zA-Z0-9]{16,}" --type ts --type js -i
# .env が .gitignore に含まれるか
cat .gitignore | grep -E "^\.env"
```

#### 4-2: 環境変数管理

```
チェック項目:
- [ ] .env が .gitignore に含まれているか
- [ ] .env.example が存在し、必要な変数が列挙されているか
- [ ] クライアントサイドに公開される変数が適切か（NEXT_PUBLIC_ 等）
- [ ] 本番環境の秘密鍵がソースコードに含まれていないか
```

#### 4-3: 基本的な脆弱性

```
チェック項目:
- [ ] ユーザー入力のサニタイズがされているか
- [ ] CORS設定が適切か（ワイルドカード許可でないか）
- [ ] 認証が必要なAPIにミドルウェアが適用されているか
- [ ] SQLインジェクション対策（パラメータ化クエリ）
```

### ステップ5: 可観測性チェック

本番で問題が起きたとき、気づけるか・調査できるかを確認する。

#### 5-1: エラートラッキング

```
チェック項目:
- [ ] Sentry等のエラートラッキングが導入されているか
- [ ] グローバルエラーハンドラーが設定されているか
- [ ] ソースマップがアップロードされるか
- [ ] 重要なcatch句でエラーが握りつぶされていないか
```

**検出方法**:

```bash
# エラーの握りつぶしを検索
rg "catch.*\{[\s]*\}" --multiline
# console.error のみで終わっている箇所
rg "catch.*console\.(error|log)" --type ts --type tsx
```

#### 5-2: アナリティクス

```
チェック項目:
- [ ] 基本的なページビュー計測が入っているか
- [ ] 主要なユーザーアクションのイベント計測があるか
- [ ] コンバージョンポイント（登録、購入等）の計測があるか
```

#### 5-3: ログ

```
チェック項目:
- [ ] 構造化ログが使用されているか（console.logだけでないか）
- [ ] API リクエスト/レスポンスのログがあるか
- [ ] エラーログに十分なコンテキスト（ユーザーID、リクエストID等）が含まれるか
```

### ステップ6: レポート生成

全チェック項目を PASS / WARN / FAIL で評価し、レポートを生成する。

**判定基準**:
- **PASS**: 問題なし
- **WARN**: 改善推奨だが出荷は可能
- **FAIL**: 出荷前に修正必須

## 出力ファイル

- `docs/ship-check-[YYYY-MM-DD].md` - 監査レポート

### レポートテンプレート

```markdown
# Ship Check レポート

実施日: [日付]
リリース種別: [初回リリース / 機能追加 / ホットフィックス]
総合判定: [PASS / WARN / FAIL]

## サマリー

| カテゴリ | 判定 | 重要な指摘 |
|---------|------|-----------|
| UX | PASS/WARN/FAIL | [概要] |
| パフォーマンス | PASS/WARN/FAIL | [概要] |
| セキュリティ | PASS/WARN/FAIL | [概要] |
| 可観測性 | PASS/WARN/FAIL | [概要] |

## FAIL項目（修正必須）

### [FAIL-1] [タイトル]
- **カテゴリ**: [UX/パフォーマンス/セキュリティ/可観測性]
- **問題**: [具体的な問題]
- **影響**: [ユーザーやビジネスへの影響]
- **修正案**: [具体的な対応策]
- **該当ファイル**: [ファイルパス:行番号]

## WARN項目（改善推奨）

### [WARN-1] [タイトル]
- **カテゴリ**: [カテゴリ]
- **問題**: [具体的な問題]
- **推奨対応**: [改善案]

## PASS項目

- [x] [チェック済み項目1]
- [x] [チェック済み項目2]

## 次のアクション
1. [ ] [FAIL項目の修正]
2. [ ] [WARN項目の対応（任意）]
3. [ ] [修正後の再チェック]
```

## リリース種別ごとのチェック範囲

| チェック項目 | 初回リリース | 機能追加 | ホットフィックス |
|------------|-------------|---------|---------------|
| 空の状態 | 全画面 | 新機能のみ | - |
| オンボーディング | 全フロー | 新フローのみ | - |
| エラーUX | 全フォーム | 新機能のみ | 修正箇所のみ |
| 画像最適化 | 全画像 | 新画像のみ | - |
| バンドルサイズ | 全体 | 差分 | - |
| セキュリティ | 全体 | 新コードのみ | 修正箇所のみ |
| 可観測性 | 全体 | 新機能のみ | - |
| 収益化 | 全体 | - | - |
| プラットフォーム依存 | 全体 | 新連携のみ | - |
