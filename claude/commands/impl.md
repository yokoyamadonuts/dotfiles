# /impl - TDD開発コマンド

`developing` スキルのTDDワークフローを、フェーズ単位の承認ゲート付きで実行するオーケストレータ。

> **方法論のSSOT（本コマンドでは再説明しない）**
> - `developing` スキル - TDDサイクル・設計原則・品質基準
> - `writing-tests` スキル - テスト作成（REDフェーズで使用）

## 使い方

```
/impl ログインフォームにバリデーションを追加
/impl            # 引数なし: タスク説明を質問する
```

## [1/4] タスク準備

1. タスク説明を取得（`$1` が空なら具体的なタスク説明をユーザーに質問）
2. `docs/DESIGN.md` / `docs/TODO.md` があれば読み込む
   - TODO.md がある場合: フェーズ構成と `[RED]/[GREEN]/[REFACTOR]` タスクをそのまま実行計画にする
   - ない場合: タスクを機能単位に分割し、機能ごとに RED→GREEN→REFACTOR のタスクを組む
3. 現在のフェーズのタスクをTodoWriteに登録する

## [2/4] フェーズ実行

各機能について、インターフェース設計 → RED → GREEN → REFACTOR の順で進める。
タスク完了ごとに TODO.md の該当行を `[x]` に更新する。

### インターフェース設計

実装前に型定義・関数シグネチャ（入力・戻り値・例外）を確定させる。

### RED（テスト作成）

`writing-tests` スキルを使用してテストを作成し、サブエージェントでテストを実行して**失敗を確認**する。
テストが「正しい理由で」失敗すること（実装がない→コンパイルエラー、実装が不完全→アサーションエラー）。

### GREEN（実装）

テストを通過する最小限の実装を行い、サブエージェントでテスト実行して**成功を確認**する。
将来の要件の先取りや過度な抽象化はしない。

### REFACTOR（リファクタリング）

テストが通った状態で、`developing` スキルの設計原則（SOLID・高凝集度・低結合度・DRY・YAGNI・テスタビリティ）に照らしてコードを改善する。優先順位:

1. テスタビリティの確保（DI・純粋関数化）
2. 単一責任の徹底
3. 重複の排除
4. 命名の改善

改善後、サブエージェントでテスト実行して成功を確認する。

### テスト実行（サブエージェント委譲）

トークン消費を抑えるため、テスト実行はサブエージェントに委譲する:

```javascript
Task({
  description: "テスト実行",
  prompt: `プロジェクトのテストを実行し、結果を報告してください。
テストコマンド: [プロジェクトに応じたコマンド]
報告形式:
- 全テスト成功: "SUCCESS: X tests passed"
- 失敗あり: "FAILED:" + 失敗したテスト名とエラーメッセージのみ（成功したテストの詳細は不要）`,
  subagent_type: "general-purpose",
  model: "haiku"
})
```

## [3/4] フェーズ承認

フェーズ内の全タスク完了後:

1. **セルフレビュー**: サブエージェント（Explore, model: opus）に変更ファイルのレビューを委譲する。
   観点は `/review` コマンドの5観点（TDD/テスト品質・コード品質・セキュリティ・アーキテクチャ・プロジェクトルール準拠）。
   報告は Critical/Warning のみ。問題があれば修正→テスト→再レビューを問題ゼロまで繰り返す。
2. **品質チェック**: プロジェクトの lint / format / build / test を実行し、通過するまで修正する。
3. **承認ゲート**: AskUserQuestionで実装内容・変更ファイル・テスト結果を提示し、次フェーズへの承認を得る。
   承認されるまで勝手に次フェーズへ進まない。

## [4/4] 完了処理

全フェーズ完了後、実装内容・変更ファイル・テスト結果のサマリーを提示し、
コミットする場合は `committer` エージェントに委譲する。
